# v0.4.0 — Conversational SH ↔ Senior Architecture

**Status:** design approved, not yet implemented
**Date:** 2026-09-17
**Revert anchor:** `aea134c` — *refactor: delete the extractor tier and the worker prose protocol*
**Experiment branch:** `exp/v0.4-conversational`, cut from `main` at `aea134c`
**Supersedes for v0.4.0 only:** the LLMCompiler loop in `agent/v0/orchestrator.py`

---

## 1. The problem

The v0.3.0 orchestrator is `planner → parallel executor → joiner → (REPLAN → planner)`,
capped at `MAX_PLAN_ROUNDS = 3` (`agent/v0/orchestrator.py:42`). Two independent
amnesias make it expensive:

- **Workers have no memory at all.** Every delegated task runs in a fresh session with a
  new `thread_id` (`splunk_subagent.py:_run`). A replan round therefore re-briefs a
  brand-new worker from zero. The only thing that survives is `build_handoff_digest()` —
  1500 characters, last three attempts (`orchestrator.py:235`).
- **SH forgets too, then pays to be reminded.** Its thread is windowed at
  `MAX_HISTORY_MSGS = 24`, and each joiner turn re-feeds a freshly assembled
  `task results + ledger + handoff digests` block describing work SH already watched
  happen.

So the system spends tokens telling agents things they were told before, and spends
iterations re-deriving ground a previous round already covered. `run_0.2` burned $26.53
on replacement workers re-running discovery from zero; v0.2's full run cost $31.36 for
net-zero score gain.

The v0.4.0 hypothesis: **replace replanning with a bounded conversation.** Keep a small
number of seniors alive for the life of a question, let them report progress often, and
let SH steer them — instead of killing them and re-briefing their replacements.

## 2. Architecture

### 2.1 The loop

```
SH.spawn(1 senior)
      |
      v
 +--> senior works <=8 iterations --> standardized MD report --+
 |                                                             |
 |   SH grades it (R1/R2/R3) and routes -- one route per senior |
 |   per wave, all in a single SH turn:                         |
 |      COMMAND  continue | retry  ----------------------------+
 |      CRITIC   flaw / why_it_fails / fix_directive ----------+
 |      CLARIFY  no tools, answered from memory ---------------+
 |      SPAWN    another senior, only when justified ----------+
 |      RETIRE   writes handoff.md ----------------------------+
 |
 +----- ANSWER (grounded AND R1 != FAIL) -------------> question done
```

A question also ends when rounds or SH turns run out — see §4.2.

Removed outright: the joiner node, `JOINER_SYSTEM_PROMPT`, the `REPLAN:` parse, the
per-round re-briefing block, and `MAX_PLAN_ROUNDS`. SH decides the final answer directly
from reports it watched arrive plus the conversation thread it participated in.

### 2.2 The boundary rule

Written into both system prompts and enforced by the route schemas:

> **SH speaks in constraints and goals. The senior speaks in evidence and SPL.**

SH never phrases a directive as a query. It says *what must be established* and *where to
look*, because scope allocation is genuinely SH's job — it holds the case file and
cross-question memory — and writing SPL genuinely is not. This is what stops SH from
being dragged into a job it cannot do, which was the failure mode this design had to
avoid.

`scope_change` is the one lever that belongs to SH alone. It is how SH acts on a
`NOT_FOUND` without writing a single query.

### 2.3 Senior lifecycle

- **Question-scoped.** Spawned for one problem statement, all retired when it ends.
- **At most 3 spawns per question**, total — retiring senior #1 and spawning #3 consumes
  the budget.
- **Demand-driven.** SH starts with **one** senior. A second or third requires a stated
  reason the current senior's constraints cannot cover. Parallel seniors are the
  exception, not the default.
- **Domain-constrained.** Each senior owns a scope (`sourcetypes` / `sources` / `fields`)
  and is told to report why the answer is or is not inside it.
- **A senior spawned mid-question gets `min(tier round budget, waves remaining)` rounds.**
  Rounds are a question-level clock, not a per-senior allowance that resets on spawn —
  otherwise a late third spawn would silently extend the question past its ceiling.
- **Exploration workers sit outside this economy.** `spawn_type: exploration` survives
  from v0.3.0 unchanged — one-shot, cheap NIM model, returns a scope proposal, never a
  value. It does **not** consume one of the three senior slots: it is the thing you deploy
  when you cannot name a scope, and that is exactly when slots feel scarce, so charging it
  a slot would make SH avoid scouting on the questions where scouting pays most. It is
  **not graded** (§3.4 — R3 is undefined for a worker that structurally cannot produce a
  value, R2 for one with a single round). And it is **capped at 1 per question**, because
  an ungraded, unslotted spawn is otherwise free. A second exploration means the first
  failed, and the answer to that is a senior with a wide scope, not another scout.

### 2.4 Technique tags retained unchanged

`agent/v0/specialists.py` stays as-is. Its three fragments are a *technique* axis,
orthogonal to the domain constraints: domain says where to look, technique says how.

| Tag | Rule | Evidence it was added on |
|---|---|---|
| `hunter` (default) | `stats count by <entity>` over the whole population before filtering to one | Q208/Q211/Q330 died by filtering to one host first |
| `content` | Drill to raw events first, map sourcetypes second | Q303: password sat in cloud-init raw text; workers capped out before reading an event |
| `metrics` | Compute every number *in SPL*, never by hand | Q331: a worker did Tukey's fences manually and beat the correct `perc25/perc75` value |

They cost zero new code — the SPAWN route carries the tag, exactly as the planner's
`[HUNTER]` prefix does today. `metrics` clearly earns its place: it encodes a hard rule
SH cannot enforce mid-round. `hunter` and `content` now overlap with what SH's directives
do every 8 iterations, so they are candidates for pruning — **on evidence from the first
run, not on assumption.**

## 3. Data contracts

### 3.1 Senior → SH: the report

Structured output is two fields, `insight` + `report`, added to the existing
`submit_finding` tool (`agent/v0/finding.py:83`) rather than defined as a second schema.
`value` / `value_kind` / `confidence` / `evidence` / `ruled_out` keep their current
meaning and keep feeding the ledger.

- `insight`: `FOUND` | `NOT_FOUND` — the routing enum.
- `report`: markdown, following the template below. **Hard cap ~400 words.**

```
# Senior #<n> - <qid> - Round <r>
**Scope:** sourcetype=<...> | source=<...> | fields=<...>
**Insight:** FOUND | NOT_FOUND
**Candidate:** <bare value, or none>   **Confidence:** <0-100>

## Prior rounds
<One line per prior round: what it established or eliminated.
 REWRITTEN each round, never appended. Hard cap 6 lines.>

## This round
### What I ran
- <spl> -> <what came back, incl. event count>
### What it means
<FOUND:     the chain from that output to the candidate.
 NOT_FOUND: what you saw instead, and why it rules this scope out.>

## Ruled out
- <feed / entity / hypothesis> - <why>

## Open questions for SH
- <Only what SH can answer from the case: which entity is in scope, whether a
  prior finding applies, which scope to try next. Never an SPL question.>
```

The **"Prior rounds"** section is the compression mechanism. The senior restates its own
history in six lines each round instead of letting a transcript grow linearly — and
because it is self-contained, the same section doubles as the compaction artifact (§6).

**Three header fields are stamped by the runner, not written by the senior**, so they
cannot be self-reported favourably:

| Field | Source |
|---|---|
| `round`, `rounds_remaining` | the question's round clock (§4) |
| `novel_spl_count` | queries this round that this senior had not already run, diffed with `extract_spl_and_sourcetypes()` against all of its prior rounds |

`novel_spl_count == 0` is literal thrashing, and hard-fails R2 without an LLM in the loop
(§3.4).

**What the senior is told about being judged.** Not the rubric — one line of intent,
carried in the spawn prompt:

> Your report is read by SH, who is deciding whether to keep you on this scope. Write it
> so SH can tell, without having to ask: that you stayed inside your constraints and
> answered the question actually asked; that this round learned something the last one
> didn't; and whether you now hold a value that could be submitted as-is, or not yet.

Three slots the template already has. The rubric itself stays SH-side: the senior is told
what a useful report contains, never the scale it is scored on.

### 3.2 SH → senior: the six routes

SH's turn emits one route per senior it addresses, as strict structured output
(`json_schema`, `strict=True`) — the same discipline the planner uses today, so a
malformed route fails the call instead of silently degrading.

| Route | Payload |
|---|---|
| **SPAWN** | `constraints{sourcetypes, sources, fields}`, `technique`, `subquestion`, `reason` |
| **RETIRE** | `target`, `reason` |
| **COMMAND** | `target`, `decision`, `rationale`, `directive`, `scope_change \| null` |
| **CRITIC** | `target`, `basis`, `flaw`, `why_it_fails`, `fix_directive`, `scope_change \| null` |
| **CLARIFY** | `target`, `reason`, `questions[1..3]` |
| **ANSWER** | `value`, `value_kind`, `source_senior`, `justification`, `case_updates[]` |

**COMMAND `decision` — `continue | retry` only:**

- `continue` — direction is right, go further. `directive` extends the hunt.
- `retry` — the approach was wrong; same question, different angle. `directive` redirects.

`rationale` is 1-2 sentences from the *case's* perspective. `directive` states a **goal**,
never SPL.

**CRITIC is its own route rather than a third `decision` value.** Three reasons. The
critic prompt must differ from the continue/retry prompt, and with one COMMAND block there
is nowhere for route-specific prompt text to live. Its `fix_directive` is a genuinely
different instruction — conditional and exploratory rather than an extension of the
current hunt — and one prompt producing both yields a mushy average. And under
`strict=True` the house pattern has no optional fields (`plan_schema.py` expresses absence
as an empty string), so a `flaw` field inside COMMAND would be legally empty on a critic;
as its own schema, a critic without a flaw fails the call.

```
target          senior id
basis           internal_contradiction | conflicts_case_file |
                conflicts_other_senior | shape_mismatch |
                violates_question_constraint
flaw            what is wrong, one or two sentences
why_it_fails    how the basis demonstrates it
fix_directive   free text — see constraints below
scope_change    {sourcetypes, sources, fields} | null
```

**`basis` is a closed enum, and that is the point.** SH has no Splunk access and never
will, so a free-text "counter-example" is an invitation to invent a dataset fact — the
failure v0.3.0's joiner prompt already shouts about in capitals (`NEVER invent dataset
facts`). Every permitted basis is checkable against something SH actually holds:

| basis | checked against |
|---|---|
| `internal_contradiction` | the report itself — `ruled_out` undercutting its own conclusion, or shown SPL that does not produce the claimed value |
| `conflicts_case_file` | a verified case-file finding or a prior question's established entity |
| `conflicts_other_senior` | a sibling report from this question |
| `shape_mismatch` | `expected_shape` — wrong units, granularity or format |
| `violates_question_constraint` | the question text (Q331: "using Splunk commands only", answered with manual arithmetic) |

**There is no `other` bucket, deliberately.** A doubt that fits none of the five is not
grounds for a critic — it is a question, and the route is CLARIFY. The missing basis is a
feature: it pushes an unformed suspicion onto the cheap route instead of dressing it up as
an assertion, and it makes critics countable after the run.

**`fix_directive` is free text under two constraints**, stated in the critic prompt:

> State what to establish first, and what follows depending on what that turns up. Do not
> write the query. If a single step is the honest directive, write one step — do not
> invent a branch to fill the shape.

Not split into `first_step` / `then_conditional` on purpose. A step-shaped field pulls SH
toward step-shaped content, which is SPL, which is the boundary rule the whole design
rests on; and a mandatory branch manufactures fake conditionality on the critics whose
honest form is one blunt instruction. The cost is measurability — whether critics carried
real conditional guidance is a read of `conversation.md`, not a count. If they come back
consistently blunt, that is a schema change with evidence behind it.

**CLARIFY `reason`:** `unclear` (the report did not parse as an argument) or `suspect`
(SH doubts the discovery). **Hard rule: a clarify turn is answerable from what the senior
already holds — no tools, no new searches.** "Go find out" is always a COMMAND. This is
what keeps CLARIFY cheap and structurally distinct.

**ANSWER** keeps the existing grounding gate (`agent/v0/grounding.py`): the value must
literally appear in a senior's report or in the question text, or it is rejected back
into another SH turn.

### 3.3 Senior reply shapes

The senior is told both shapes at spawn, so it never guesses which is expected:

- **to a CLARIFY** — a short prose block, capped, appended to the thread. No tool calls.
  Does **not** consume a senior round. It *does* consume one SH turn, which is what bounds
  clarifying: a senior can be asked to explain itself only as often as SH has turns left.
- **to a COMMAND or a CRITIC** — resume work, consume a senior round, produce the next
  report. A round is a **cap, not a quota**: a senior that satisfies a critic in one
  iteration ends the round at one, so a cheap critic costs what it uses. The rule that
  separates the two routes is tool access — if the senior could answer without touching
  Splunk, it was a CLARIFY; CRITIC means *go prove or refute it*.

### 3.4 The review rubric

SH applies the same three dimensions to every report, and **emits the grades** alongside
the route — three enums per senior per round.

| | Dimension | Asks |
|---|---|---|
| **R1** | **Scope alignment** | Did the senior work inside its constraints, and address *this* problem statement rather than a neighbouring one? |
| **R2** | **Progress** | Did this round produce information the prior rounds did not have? |
| **R3** | **Answer readiness** | Is there a candidate in submittable shape, or prose / a hedge / nothing? |

Each is `PASS` / `WEAK` / `FAIL`. SH's per-wave structured output is a list of:

```
senior_id
r1_scope_alignment   PASS | WEAK | FAIL
r2_progress          PASS | WEAK | FAIL
r3_answer_readiness  PASS | WEAK | FAIL
route                SPAWN | RETIRE | COMMAND | CRITIC | CLARIFY | ANSWER
<route payload>
```

**Two dimensions were considered and rejected as duplicates of existing machinery.** An
*evidence quality* dimension ("is the claim backed by SPL that was actually shown") is
already covered twice — `extract_spl_and_sourcetypes()` harvests every query from the
transcript mechanically, and the grounding gate blocks any ANSWER whose value is absent
from the evidence. A *calibration* dimension ("does confidence match the claim") is
enforced in code: `finding.py` demotes `solved` below `SOLVED_MIN_CONFIDENCE = 50` to
`partial`.

**R2 has two independent FAIL sources, and this matters.** A floor enforced on SH's own
grade is dodgeable by never grading FAIL — the constraint and the constrained would be the
same judgement. So:

- **Code**: `novel_spl_count == 0` → hard `FAIL`, not overridable by SH. Literal repetition
  needs no judgement to detect.
- **SH**: may *additionally* grade `FAIL` when the queries were new but the round learned
  nothing. Code cannot see novel-but-useless; SH reading two consecutive reports can.

Neither alone suffices — code under-detects, SH over-trusts its own workers.

**Two gates.**

| Gate | Rule | Why |
|---|---|---|
| **Anti-thrash** | Two consecutive `R2 = FAIL` from **either** source → `continue` is blocked for that senior. SH must RETIRE it or change its scope. | This is what is supposed to keep actuals below the §4.1 ceiling. |
| **Wrong-question** | `R1 = FAIL` on the source report → the `ANSWER` route is blocked. | A value can be real, grounded and well-formed and still answer something adjacent to what was asked. The grounding gate waves that straight through, because the value genuinely appears in the evidence. It is the one failure the existing machinery is blind to. |

R3 is deliberately **not** gated — `answer_shaped()` already rejects unsubmittable values
at the boundary. R2 is deliberately **not** gated on ANSWER — a senior that made no
progress *this* round may have found the answer two rounds ago, and blocking on stale
progress would force spending on an already-solved question.

**Grades exist to be counted, not just consulted.** The anti-thrash gate needs last
round's grade to be readable at this round's decision point, which rules out a grade that
lives only inside a prior turn's reasoning. And it turns §10's weakest criterion into a
table: grade distribution, `continue`-rate conditional on grade, and the outright
contradictions — `continue` issued on a FAIL, `ANSWER` taken from a WEAK-scope report.
`spawn_report.py` already does this shape of calibration analysis for SH's spawn
confidence, so there is a pattern to follow. An all-`PASS` column after three questions
means the rubric is inert and the run can be killed early.

The honest limitation: a model that grades before routing anchors its route on the grade
it just wrote, so the grades are not an independent measurement of the routing. They are
part of the same decision. That is the intended coupling — the grade *should* constrain
the route — but it means the table shows consistency, not correctness.

**Exploration workers are not graded** (§2.3).

## 4. Budgets

Derived from `test_20260915_174228` (25 workers, all five questions at 1000 pt):
iterations min 8 / mean 16 / max 26; **three workers ran to the 25-iteration cap and all
three still ended `partial`**; 21/25 ended `partial` overall; the only two `solved`
results arrived at 9 and 16 iterations.

**One iteration = one agent-node call** = one LLM turn by the worker
(`splunk_agent.py:152,548`). The graph is `agent -> verify -> execute -> agent`, so a
search costs one iteration to issue and the next iteration reads its result. Measured
ratio: ~1.5-3 iterations per SPL query. **8 iterations ≈ 3-5 searches.**

Question tiers come from `base_points`: 100 (24 questions), 500 (23), 1000 (9).

| Tier | Seniors max | Rounds per senior | Iterations per round | Ceiling per senior | Question ceiling | SH turns |
|---|---|---|---|---|---|---|
| **100 pt** | 1 | 3 | 8 | 24 | 24 | ~5 |
| **500 pt** | 2 | 5 | 8 | 40 | 80 | ~8 |
| **1000 pt** | 3 | 8 | 8 | 64 | 192 | ~12 |

### 4.1 Known risk, to be measured not assumed

The 1000-pt ceiling of 192 senior-iterations is **2.4x the 80 measured today**. It is a
ceiling, not a schedule: demand-driven spawning and early retirement are what are supposed
to keep actual spend far below it. That is a hypothesis, and the first smoke test must
answer it with a number, so the run records **actual senior-iterations per question
against the ceiling** and per-question cost. If actuals track the ceiling rather than the
baseline, the experiment has failed on cost regardless of score.

### 4.2 When a question ends

Exactly three conditions, whichever comes first:

1. **SH takes the `ANSWER` route and it holds** — the value is grounded (it appears
   literally in a senior's report or the question text) and the source report is not
   graded `R1 = FAIL`. Both conditions, not either: grounded-but-off-scope is the case
   §3.4's wrong-question gate exists for.
2. **Rounds run out** — the tier's round budget (3 / 5 / 8) is spent across all seniors.
3. **SH turns run out** — the tier's turn budget (~5 / ~8 / ~12) is spent.

Both budgets are named because they are independently exhaustible: clarify turns consume
SH turns without consuming senior rounds, so a question can run out of turns with rounds
left, or out of rounds with turns left. On either exhaustion the answer falls back to
`best_candidate()` over every report this question produced (§8).

A COMMAND or CRITIC aimed at a senior with zero rounds remaining is rejected by the schema
validator rather than silently dropped — SH's remaining options there are RETIRE or ANSWER.

### 4.3 Why SH turns stay cheap

Seniors run in **parallel waves**, and SH reads a whole wave in a single turn, emitting
one route per senior. Eight rounds therefore cost eight SH turns, not twenty-four. Had SH
burned a turn per report, its cost would have risen ~10x — the $31 territory the
cost-limited-runs policy exists to prevent.

## 6. Context management

A senior's context size is the `prompt_tokens` of its most recent call, which
`usage_tracker` already records — tracking is a dict lookup, not new plumbing.

**Predictive, checked at round start:**

```
projected = current_context + (8 * this senior's measured mean tokens/iteration)
if projected > 0.80 * SENIOR_CONTEXT_WINDOW:  compact before working
if current   > 0.70 * SENIOR_CONTEXT_WINDOW:  print an operator alert
```

Compacting at the *start* of a round guarantees the senior has room for the whole round,
rather than discovering mid-round that it does not.

**Compaction needs no new prompt.** The senior's own latest report is already the
compressed state — that is what "Prior rounds" was designed for. The thread is rebuilt as
`[system prompt, latest report, current directive]` and the transcript is dropped.

### 6.1 Where the window number comes from

`SENIOR_CONTEXT_WINDOW` is a per-model lookup living beside `PRICES_PER_1M` in
`agent/v0/usage_tracker.py` — same file, same keying by model id, same "verify before each
full run" discipline the price table already carries. One table to check, not two places
to forget.

**The rule is: record the window the PROVIDER serves, not the one the model card
declares.** These differ, often by a lot, and the model card is the wrong number:

| Model | Served | Checkpoint declares |
|---|---|---|
| `zai-org/GLM-5.3` (Featherless) | **256 000** | 1 048 576 |

Featherless serves 256K as a cost/performance tradeoff against a native 1M window. Tools
that read the checkpoint value instead of the served one are a known class of bug.

**Round down when unsure**, because the failure is asymmetric. A window set too low
compacts earlier than necessary and wastes a little; a window set too high overflows the
context mid-round, which is a hard failure that costs the round. 256K is the safe reading
here for a second reason: the Featherless figure is published for GLM-5.3-**Flash**, and
the id this project prices is plain `zai-org/GLM-5.3`. Unconfirmed either way, and
under-estimating is the cheap direction to be wrong in.

**For a model added later**, look the served window up from the provider's own
documentation at the time it is added — the same moment `CLAUDE.md` already requires
asking for its price and adding a `PRICES_PER_1M` row. One lookup, two numbers, one
table.

## 7. Retirement and handoff

Every retirement writes `handoffs/senior_<n>_handoff.md`: the report template plus a
final **"What I'd tell my replacement"** section. Retirement happens on three triggers:

1. SH routes RETIRE (senior judged unproductive).
2. The senior exhausts its round budget.
3. End of question — all survivors are swept.

End-of-question handoffs feed the case file (`agent/v0/case_file.py`), which is how a
question's dead ends reach the next question instead of dying with the worker.

**A retirement caused by `api_failed` or `runaway` does not consume a spawn slot.** A
transport failure is not a reasoning outcome, and charging it against the 3-spawn cap
would let one provider hiccup silently halve a question's budget.

## 8. Error handling

| Failure | Behaviour |
|---|---|
| Senior crashes (`api_failed`) | Existing status preserved; retired; spawn slot refunded; HITL interrupt path unchanged |
| Senior blows `OUTPUT_TOKEN_CAP` (`runaway`) | Retired; spawn slot refunded; HITL interrupt |
| SH emits malformed route | `strict=True` json_schema fails the call — no silent degradation to a default route |
| SH exhausts turn budget without ANSWER | Fall back to `best_candidate()` over every report this question produced (existing `grounding.py` helper) |
| ANSWER fails the grounding gate | Rejected back into one more SH turn; on the second failure, fall back as above |
| Report exceeds the word cap | Truncated at the cap with a logged warning; `value`/`confidence` are unaffected because they are separate schema fields |

## 9. Testing

Unit tests (no live LLM, no live Splunk):

- Route schema parse/reject — one test per route, plus a malformed-route rejection.
- Budget table — tier -> (seniors, rounds, iterations) for 100/500/1000.
- Spawn-cap accounting, including the `api_failed`/`runaway` refund.
- Compaction trigger arithmetic at the 70% and 80% boundaries.
- Report template validation: word cap, required sections, `Prior rounds` <= 6 lines.
- `conversation.md` rendering for each message type.
- CLARIFY replies do not consume a round and carry no tool calls.
- Rubric grades are emitted for every senior in every wave, and never for an exploration
  worker.
- `novel_spl_count` diffing: a repeated query counts as zero novel, a new one as one.
- Both R2 FAIL sources independently, and the anti-thrash gate firing on a mixed pair
  (one code FAIL, one SH FAIL).
- Code's `R2 = FAIL` is not overridable by an SH grade of `PASS`.
- `R1 = FAIL` blocks the ANSWER route; `R2 = FAIL` and `R3 = FAIL` do not.
- CRITIC schema rejects a missing `flaw`, and rejects a `basis` outside the five enums.
- COMMAND schema rejects `decision: critic` — it is a separate route now.
- Exploration cap: a second exploration spawn on one question is refused, and neither
  spawn decrements the 3-senior slot count.
- Termination: each of the three end conditions fires, and ANSWER does not terminate a
  question when the source report is graded `R1 = FAIL`.

Integration: **a smoke test on 5 hard questions only**, per the active cost-limited-runs
policy — `python agent/v0/run_all_v0.py --ids Q216 Q217 Q224 Q328 Q329`, output to
`log/temp/`. **No full run without explicit user go-ahead.**

## 10. Success criteria

The experiment is judged on four readings from that smoke test, against
`test_20260915_174228` as the baseline (0/5 correct, $1.3589 total, $0.272/question):

1. **Score** — must beat 0/5. This is the point of the exercise.
2. **Cost per question** — must not exceed ~2x baseline. Above that the ceiling risk in
   §4.1 has materialised and the design loses on economics.
3. **Actual vs ceiling senior-iterations** — if actuals track the 192 ceiling rather than
   the 80 baseline, demand-driven spawning did not work and the retirement logic needs
   rethinking before any full run.

4. **Is SH verifying or rubber-stamping?** No longer a read of the transcripts — the
   emitted grades make it a table:

   - grade distribution across all three dimensions (an all-`PASS` column means the rubric
     is inert);
   - `continue`-rate conditional on `R2` grade (if it does not fall as the grade falls,
     SH is not acting on its own judgement);
   - contradiction counts — `continue` issued after a `FAIL`, `ANSWER` attempted from a
     `WEAK`-scope report, critics raised per `basis`;
   - `novel_spl_count` distribution, which answers §4.1 directly: frequent zeros mean
     seniors are thrashing and the 192-iteration ceiling is being approached for nothing.

## 11. Change ledger — GENERAL vs EXPERIMENT

Two categories, tracked separately for the whole of v0.4.0, because a failed experiment
must revert without taking real fixes with it.

**GENERAL** — lands on `main` as identified, survives a failed experiment. Anything that
would be a fix or improvement regardless of which orchestrator is running: shared-module
bugs, logging, the usage tracker, the Splunk client, the worker graph, docs.

**EXPERIMENT** — lives only on `exp/v0.4-conversational`. The conversation loop, the
route schemas, the report template, the thread log, the context tracker, the removal of
the joiner.

At the end of the experiment: general changes are already on `main`; if the experiment
fails, `git branch -D exp/v0.4-conversational` and nothing else is needed. Both
changelogs live in `docs/version_architecture/v0/v0.4.0.md` and are written **in the same
turn as each change**, per `CLAUDE.md`.

## 12. Future work (recorded, not built)

**A difficulty router.** Every budget in §4 keys off `base_points`, which BOTSv3 supplies
free. Real-world questions arrive with no such label, so this scheme does not transfer off
BOTS without something that classifies difficulty first. Three candidates, cheapest first:

1. **Feature heuristic** — entity count in the question, whether a feed is named, whether
   the answer is a scalar or a list, whether it requires a join across sourcetypes.
2. **Embedding nearest-neighbour** — embed the question, take the tier of its k nearest
   labelled BOTSv3 questions. Needs no training and reuses the 56 labelled examples.
3. **Cheap LLM classifier** — one call to a small model returning a tier plus a rationale.
   Most accurate, most expensive, and the only one that can explain itself.

The router only has to be approximately right: the tier sets a ceiling, and demand-driven
spawning already keeps easy questions cheap inside a generous one.

**Pruning the technique axis.** `hunter` and `content` may be redundant once SH issues a
directive every 8 iterations. Decide from the first run's `conversation.md`, not from
argument.
