# SIEM Agent v0.1 — Connection Pool + Token Tracking

> **Code**: `agent/v0/`
> **Predecessor**: [v0.0](v0.0.md) — hierarchical SH + Senior + Extractor, 20/58 (34.5%), $7.36.

## What changed vs v0.0

v0.1 is a combined **infrastructure + agent architecture** release. It adds a thread-safe
Splunk connection pool, exact token/cost tracking, per-run LangSmith naming, and replaces the
sequential ReAct SH loop with an LLMCompiler plan-and-execute DAG that runs Senior workers
in parallel. Senior workers also switch from gpt-5.4 to the cheaper GLM-5.2-fp8 via Vultr.

| Area | v0.0 | v0.1 |
|------|------|------|
| SH agent pattern | Sequential ReAct (one spawn_senior at a time) | LLMCompiler (parallel DAG: Planner → Executor → Joiner) |
| Senior model | gpt-5.4 (OpenAI) | GLM-5.2-fp8 (Vultr serverless) |
| Max parallel Senior workers | 1 (serial) | Up to 6 (ThreadPoolExecutor + SplunkConnectionPool) |
| Splunk sessions | 1 shared `SplunkClient` (not thread-safe) | `SplunkConnectionPool` — 6 independent sessions |
| Token tracking | None | `UsageTracker` callback — per-model, cached tokens, per-Q SH delta |
| Cost tracking | None | Per-call USD estimate from hardcoded price table; written to `run_summary.json` |
| LangSmith project | Hardcoded `"V1.1"` in `.env` | Auto-named `botsv3-run_1.x` / `botsv3-test_<ts>` per run |

## SplunkConnectionPool

### Why it was needed

v0.0 created one `SplunkClient` (one `requests.Session`) at startup and shared it across the
SH and all Senior workers. `requests.Session` is not thread-safe for concurrent writes — the
auth header is shared mutable state. v0.0 worked only because the v0 execution model is fully
serial (SH waits for each Senior to finish before spawning the next). The moment Senior workers
run concurrently, the single session becomes a race condition.

### Design

`agent/splunk_pool.py` holds `N` fully-authenticated `SplunkClient` instances in a
`queue.Queue`. Each call to `.search()` / `.get_field_values()` / `.get_sourcetype_fields()` /
`.sample_events()` atomically checks out one client for the lifetime of that search, then
returns it to the queue. If all slots are occupied, the caller blocks (up to `checkout_timeout`
seconds, default 60 s).

```
startup:  N × SplunkClient(login)  →  queue of N slots

call:     queue.get()   ← blocks if all N busy
          SplunkClient.search(...)   (owns the session for the full job cycle)
          queue.put()   ← always runs (finally block)

401:      re-login on that slot → retry once → queue.put()
```

It is a **drop-in replacement** for `SplunkClient` — identical public API, no call-site changes
needed anywhere in `splunk_agent.py` or the v0 subagent.

### Concurrency benchmark

**Date:** 2026-07-01  
**Machine:** Local Windows 11 (same host as the Splunk instance)  
**Test query:**
```spl
index=botsv3 sourcetype="stream:http" | stats count by src_ip | head 20
```
This query was chosen because it touches a realistic-size sourcetype, aggregates, and returns
results fast enough to measure scheduler contention without timing noise from slow data scans.

**Baseline (serial, single session, 5 repetitions):** mean = **3.37 s**, min = 3.16 s, max = 4.18 s

| Concurrent | Pool | Wall (s) | Per-job (s) | Slowdown | Failures | Jobs/s |
|:----------:|:----:|:--------:|:-----------:|:--------:|:--------:|:------:|
| 1  | 1  | 3.18  | 3.18  | 0.9× | 0 | 0.31 |
| 2  | 2  | 3.21  | 3.20  | 0.9× | 0 | 0.62 |
| 3  | 3  | 4.30  | 4.30  | 1.3× | 0 | 0.70 |
| 4  | 4  | 4.36  | 4.33  | 1.3× | 0 | 0.92 |
| 5  | 5  | 5.80  | 5.65  | 1.7× | 0 | 0.86 |
| **6**  | **6**  | **5.85**  | **5.66**  | **1.7×** | **0** | **1.03 ← peak** |
| **7**  | **7**  | **6.77**  | **6.09**  | **1.8×** | **0** | **1.03 ← peak** |
| 8  | 8  | 8.17  | 7.57  | 2.2× | 0 | 0.98 |
| 10 | 10 | 10.10 | 8.88  | 2.6× | 0 | 0.99 |
| 12 | 12 | 14.49 | 13.95 | 4.1× | 0 | 0.83 |
| 15 | 15 | 16.66 | 12.59 | 3.7× | 0 | 0.90 |
| 20 | 20 | 22.01 | 15.43 | 4.6× | 2 | 0.91 |

**Columns:** `Wall` = total elapsed for all N jobs to finish; `Per-job` = mean time per individual
search; `Slowdown` = Per-job ÷ baseline; `Jobs/s` = N ÷ Wall.

#### Three zones

**Zone 1 — Free gain (1–2 concurrent)**
Adding a second session costs nothing per job (0.9× = no measurable slowdown). Throughput
doubles from 0.31 → 0.62 jobs/s because Splunk overlaps I/O wait across the two jobs.

**Zone 2 — Diminishing returns (3–8 concurrent)**
Each extra session slows individual searches (Splunk's search scheduler queues jobs), but
wall-clock throughput still rises because the overlap benefit outweighs the queuing penalty.
Throughput peaks at **1.03 jobs/s at 6–7 concurrent** (3.3× faster than serial), with only a
1.7–1.8× per-job slowdown cost.

**Zone 3 — Degradation (10–20 concurrent)**
Splunk's scheduler becomes saturated. Per-job latency spikes to 4.1× at 12 concurrent.
Throughput actually falls below the 6-slot peak. At 20 concurrent, 2 out of 20 searches fail.

#### Decision: pool size = 6

Size 6 is the measured optimum for this host. It delivers maximum throughput (1.03 jobs/s,
3.3× serial) while keeping per-job slowdown at a predictable 1.7×. Sizes 7–8 tie in
throughput but cost more per search; 9+ buys nothing and risks failures.

> **Note:** These figures are specific to this Windows 11 host running Splunk Enterprise locally.
> If the Splunk instance is moved to a separate server or given more CPU/memory, re-run the
> benchmark (`agent/splunk_pool.py` benchmark section in the docstring has the test script).

## UsageTracker — token and cost tracking

### Problem

v0.0 had no way to know how many tokens each run consumed or what it cost. LangSmith shows
token counts but its cost estimates are unreliable for new models (e.g. `gpt-5.4` was not in
LangSmith's price table as of 2026-07). The Extractor uses the raw OpenAI SDK so it never
appears in LangSmith at all.

### Design

`agent/v0/usage_tracker.py` implements a `BaseCallbackHandler` subclass registered on every
`graph.invoke()` config dict (`config["callbacks"] = [tracker]`). LangChain/LangGraph
propagates this callback to all LLM calls inside the graph via Python's `contextvars`, so every
`ChatOpenAI.invoke()` inside the SH and Senior worker graphs fires `on_llm_end` on the tracker.

The Extractor (raw `openai.OpenAI` SDK, not LangChain) calls `tracker.add_nim_usage()` directly
after each completion, passing `resp.usage.prompt_tokens`, `resp.usage.completion_tokens`, and
`resp.usage.prompt_tokens_details.cached_tokens`.

```
SH graph.invoke(config={"callbacks":[tracker], "tags":["SH",qid]})
  └─ every ChatOpenAI call → on_llm_end(response, tags=["SH",qid])
       → _lc[model].input_tokens  += prompt_tokens
       → _lc[model].cached_tokens += cached_tokens
       → _lc[model].output_tokens += completion_tokens
       → if "SH" in tags: _sh_cum += delta        ← per-question SH reporting

Senior graph.invoke(config={"callbacks":[tracker], "tags":["senior",qid]})
  └─ every ChatOpenAI call → on_llm_end(response, tags=["senior",qid])
       → _lc[model] += ...                         ← goes to model bucket, NOT SH bucket

Extractor.extract() → resp = openai.Client.chat.completions.create(...)
  └─ tracker.add_nim_usage(model, inp, cached, out) → _nim[model] += ...
```

### Cost calculation

GPT-5.4 has **tiered pricing** (short context < 272 K tokens vs long context ≥ 272 K), so the
per-call cost is evaluated at call time using `prompt_tokens` to determine the tier:

```
non_cached = prompt_tokens - cached_tokens
cost = non_cached        × input_price  / 1M
     + cached_tokens     × cached_price / 1M
     + completion_tokens × output_price / 1M
```

Price table in `PRICES_PER_1M` (as of 2026-07, verify before each run):

| Model | Input /1M | Cached /1M | Output /1M | Long-ctx threshold |
|-------|:---------:|:----------:|:----------:|:-----------------:|
| gpt-5.4 (short) | $2.50 | $0.25 | $15.00 | < 272 K tokens |
| gpt-5.4 (long)  | $5.00 | $0.50 | $22.50 | ≥ 272 K tokens |
| gpt-5.4-mini    | $0.75 | $0.075 | $4.50 | — |
| GLM-5.2-fp8     | $0.85 | — | $3.10 | — |
| meta/llama-3.3-70b-instruct (NIM) | $0.23 | — | $0.40 | — |

### Per-question SH token report

At the end of every question the runner prints and logs:

```
SH tokens [Q1]: input=12,345  cached=8,100  output=423  est=$0.0423
```

This is the SH's own consumption for that question (Senior and Extractor tokens are tracked
separately in the model buckets but not broken out per-question).

## LangSmith project naming

v0.0 had `LANGSMITH_PROJECT="V1.1"` hardcoded in `.env` and the code set the legacy
`LANGCHAIN_PROJECT` env var (which `LANGSMITH_PROJECT` silently overrides). Every run — full
or test — landed in the same `"V1.1"` project in LangSmith, making traces from different runs
indistinguishable.

v0.1 fixes both issues:
- `.env` no longer sets `LANGSMITH_PROJECT`
- `run_all_v0.py` sets `os.environ["LANGSMITH_PROJECT"]` at startup, **after** `load_dotenv()`
  so it always wins
- Project name is derived from the `RunLogger` name: `botsv3-run_1.x` for full runs,
  `botsv3-test_<YYYYMMDD_HHMMSS>` for test runs

Each run is now its own isolated project in LangSmith, filterable by name.

## LLMCompiler — parallel task DAG

### Why the ReAct loop was a bottleneck

v0.0's SH used a standard ReAct loop: call `spawn_senior(subquestion)` → wait for result → decide
next action → repeat. Every Senior worker ran serially, even when two sub-questions were
completely independent (e.g. "find the malware hash" and "find the C2 IP" in the same APT
question). Wall-clock time per question scaled linearly with the number of delegations.

### Design (inspired by LLMCompiler)

`agent/v0/orchestrator.py` replaces the tool-calling ReAct graph with a three-node LangGraph:

```
[Planner] → [Executor] → [Joiner] → (Replan once if needed | END)
```

**Planner node** (one LLM call per question):
The SH LLM receives a system prompt asking it to output a numbered task DAG:

```
PLAN:
- Goal: find the C2 domain
- Prior knowledge: host wrk-klagerf compromised, APT actor seen in sysmon
- Approach: dns + network flow logs

TASKS:
1. Search dns logs on wrk-klagerf for unusual outbound lookups Aug 2018
2. Search stream:http for beaconing from wrk-klagerf in Aug 2018
3. Given $1 and $2: cross-reference the candidate domain from $1 with the HTTP host header in $2
```

Tasks without `$N` references are **dependency-free** and run in parallel. Tasks with `$N`
wait for those results, then substitute them inline before dispatching.

**Executor node** (pure Python, no LLM call):
```
remaining = all tasks
while remaining:
    ready = [t for t in remaining if all deps completed]
    dispatch ready in parallel via ThreadPoolExecutor(max_workers=6)
    wait for all to finish, collect results into completed{}
    substitute $N → result text for next wave
```

The `ThreadPoolExecutor` size matches the `SplunkConnectionPool` size (6). Each thread calls
`ctx.pool.run_senior(subquestion, qid, idx)`, which checks out one Splunk session from the
pool, runs the full v0.0.0 agent graph, and returns structured findings.

**Joiner node** (one LLM call per round):
Receives a formatted summary of all task results and must output one of:

- `FINAL ANSWER: <value>` — synthesis complete
- `REPLAN:` + new numbered tasks — one retry round allowed (max `MAX_PLAN_ROUNDS = 3`)

If neither tag is found the last non-empty line is used as a fallback answer.

### Cross-question memory

The SH graph uses a single `MemorySaver` thread (`sh_<run_name>`) across all 58 questions.
Every planner AIMessage, the joiner's task-results HumanMessage, and the joiner's FINAL ANSWER
AIMessage are all stored in the thread. The planner for Q2 therefore sees the full Q1 plan +
findings + final answer as context — the same cross-question memory behaviour as v0.0.

### Extractor-retry compatibility

When the Extractor rejects an answer, `run_all_v0.py` calls `run_sh(feedback, ...)` again.
The feedback HumanMessage is appended to the thread; the planner sees the prior conversation
and can either produce a `DIRECT ANSWER:` (from memory) or generate corrective tasks.

### Thread safety

With up to 6 concurrent Senior workers each firing LangChain `on_llm_end` callbacks, the
`UsageTracker` required a `threading.Lock()` around all counter mutations. This was added in
`agent/v0/usage_tracker.py`.

### GLM-5.2-fp8 as Senior model

All Senior workers now use **GLM-5.2-fp8** (Zhipu AI) via Vultr serverless inference
(`https://api.vultrinference.com/v1`), replacing gpt-5.4. The SH (planner + joiner) continues
to use gpt-5.4 via OpenAI. Pricing:

| Model | Role | Input /1M | Output /1M |
|-------|------|:---------:|:----------:|
| gpt-5.4 | SH planner + joiner | $2.50 (short) / $5.00 (long) | $15.00 / $22.50 |
| GLM-5.2-fp8 | Senior workers | $0.85 | $3.10 |

API key env var: `VULTR_SERVERLESS_INFERENCE_API_KEY`.  
Override via `--senior-model` / `--senior-base-url` / `--senior-api-key-env` CLI flags.
