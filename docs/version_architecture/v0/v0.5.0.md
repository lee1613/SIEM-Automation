## Why this version exists

Observed on the v0.4.5 full run, first 15 questions:

1. **Redundant RECALL.** At Q204, Q205, Q206 and Q213, SH recalled the previous question's
   summary although that question's full transcript was already in its prompt (the prompt was
   37K–97K tokens, far under the 163,200 threshold). Each spent one of the 2 recall slots and
   re-sent ~1–1.6K tokens of what SH already held.
2. **Cards and knowledge duplicate the raw transcripts below the threshold.** Every card, and
   every knowledge entry, restates a transcript that is in the prompt in full.
3. **Knowledge drops are silent about *what* was dropped.** Q213: "dropped 4 least-recent
   entries"; Q215: 13. The log gives a count, not the entries.
4. **There is no incident timeline anywhere.** v0.4.5 assumed the case file carried one; it
   does not (`case_file.py` findings and entities have no time field). Summaries mention
   times only when the question happened to be about time.
5. **Summarizing blocks the next question.** Measured: 8.1 s per summary (6.6–10.5 s, 7
   questions) against 134–1,586 s per question: ~2–3% of wall time. The operator chose to
   build the concurrency regardless, as a learning exercise in threading and crash recovery.

## Requirements (operator, 2026-09-24)

| # | requirement |
|---|---|
| R1 | The runner refuses a RECALL of a question whose transcript is still in the prompt in full, without spending a recall slot. |
| R2 | Below the threshold the prompt carries raw transcripts only: no cards, no knowledge, no timeline. Summaries are written to disk in a **background thread** while the next question starts. When the threshold is crossed the runner **waits** for summaries still in flight, then swaps and injects the summarized questions' blocks at the end of the memory. |
| R3 | Each summary records the **incident timeline**: every attacker action the transcript puts a time on — initial access, every lateral movement, escalation, persistence, exfiltration, every breakthrough. |
| R4 | Cap overflow (knowledge 6K, timeline 11K) is **verbose and catchable**: every dropped entry logged in full, an event in `events.jsonl`, a count on the metrics row. |

## Decisions

| # | decision | why |
|---|---|---|
| D1 | A card exists **only for a summarized question**; no "raw/summarized" labels. | A card's presence already means "summarized". |
| D2 | The runner tracks **one integer**, `summarized_count = k`. A recall of the question at position `i` in question order is served iff `i < k`. | Swaps are oldest-first and never undone, so the summarized questions are always a prefix (invariant I1). |
| D3 | Crash recovery **replays the exact original input** (outbox pattern): the summary job's inputs are written to `memory/pending/<QID>.pkl` before it is queued and deleted after the summary is written; at startup every leftover job is re-run through the same `summarize_question`. | One code path. Rebuilding inputs from three different files is a second path that can drift. |
| D4 | Timeline over its cap: **merge duplicates first** (same entity, same action, same minute), then cap at **11K**; entries dropped after that are logged in full. | Operator: every lateral movement must be recorded. 11K ≈ 56 questions × ~5 events × ~40 tokens. |
| D5 | Knowledge and timeline appear only after the first swap, with the summarized blocks. | Below the threshold they duplicate the raw transcripts. |
| D6 | One worker thread (`max_workers=1`). | Summaries finish in question order, so I1 holds and `load_memories`' mtime order stays question order. |

## Invariants (each has a test)

- **I1** — the summarized questions are always the first `summarized_count` questions in history order.
- **I2** — the current question is never summarized or hidden.
- **I3** — a question whose summary is still in flight is never swapped: the swap waits for it.
- **I4** — a pending job exists on disk for every queued summary until its memory file is written.
- **I5** — the summarizer's input carries nothing from the scoreboard or the answer key (as v0.4.5).

## Design

### Prompt layout

```
system prompt + briefing                       fixed
[summarized blocks: card + detail, Q1..Qk]      only once k > 0, append-only
[raw transcripts Q(k+1)..Q(n-1)]                append-only between swaps
[knowledge] [incident timeline]                 only once k > 0
case file                                       changes every question
current question
```

### R1 — `render_memory` returns a view, the runner checks the counter

`render_memory(...) -> MemoryView(messages, order, summarized_count)`, where `order` is the past
qids in question order. `_serve_recalls` refuses when `qid in order[summarized_count:]`:
*"Q213 is already in your context in full, above — nothing to recall"*; such an entry does
not count toward the 2-per-question cap, and a turn made only of such entries charges no turn.
`ledger` recalls are always served (the prompt shows only the ledger table; the JSON carries the
quotes and status history). B7's text changes to: *RECALL only a question in the MEMORY INDEX,
or any question's `ledger`.* `swapped.json` (a list) is replaced by `summarized_count` (an int).

### R2 — background summaries (operator builds, Claude guides)

```python
class SummaryQueue:                               # sh_memory.py
    def __init__(self, llm, run_dir): ...
    def submit(self, job: dict) -> None           # write memory/pending/<QID>.pkl, queue, return at once
    def wait(self) -> None                        # block until every queued job has finished
    def close(self) -> None                       # wait, then shut the worker down

def recover_pending(run_dir, queue) -> list[str]  # startup: resubmit every leftover pending job
```

A job is the exact keyword arguments of `summarize_question` minus `llm`: `qid, question,
guidance, answer, transcript, ledger_text, verified, verdicts` — the ledger is rendered to text
when the job is made, so a job is plain data and pickles. `render_memory` calls `queue.wait()`
only when the prompt is over the threshold (I3). `main()` calls `queue.close()` before exiting.
A job that raises is logged and its pending file kept, so the next start retries it.

### Consequences of threading (Claude)

- **Cost bookkeeping:** a question's metrics row is written before its summary finishes, so
  every metrics write refreshes `cost_by_role` of earlier rows from the tracker.
- **Log lock:** `sh_memory.log` takes a lock; two threads write `compaction_log.md`.
- **Tracker:** already thread-safe (`UsageTracker._lock`).

### R3 — incident timeline

`Digest.timeline: list[TimelineEvent(time, entity, event, evidence)]`; `time` as the data states
it, normalized to UTC when merged (ISO, `HH:MM:SSZ` with the question's date, epoch seconds).
Prompt rule: record every attacker action whose time the transcript establishes; never invent
a time. Merged across questions sorted by time; duplicates (same entity, same minute, same
action) merged first (D4).

### R4 — verbose caps

Every entry dropped by a cap is logged in full: `[SH MEMORY] CAP knowledge 6,000 tok exceeded
(6,412): dropped "[stream:smtp] …" (Q203)`. `events.jsonl` gets `memory_cap_exceeded {block,
cap, size, dropped}`; the metrics row gets `memory_dropped`.

## Scope added 2026-09-25 (change control: design reopened after the v0.4.5 full run)

The v0.4.5 full run ([result](../../scoreboard_result/v0/v0.4.5.md)) found that a senior's context
could pass 272K and that provider errors cost whole questions. The operator added R5–R8 to this
version. They were declined: forcing a submit when one `solved` candidate is held (the operator
prefers an honest non-answer to a guess), and re-verifying conclusions carried in from memory (the
operator expects that to resolve as earlier questions are answered correctly).

| # | requirement |
|---|---|
| R5 | A senior's context is checked **after every call**. At **80% of its window** (GLM-5.3: 204,800 of 256,000) the round stops, the senior writes a summary **in the handover template**, and it **continues on a fresh thread** seeded with that summary, for as long as its rounds last. Clarify calls are checked too. |
| R6 | Every API call has a **deadline on our side of 10 minutes**, retries included. Past it, the call is an API error and the runner carries on. The deadline must never discard a reply the model is still legitimately producing. |
| R7 | **Brief API errors are retried** (connection errors, HTTP 500/502/503/504) with waits long enough to outlast a short outage, before a senior or SH is retired. |
| R8 | **A file swap that Windows briefly locks is retried** (`PermissionError` WinError 5 on `os.replace`), everywhere the code swaps a file in. |

### Why a senior could pass 272K (the bug R5 fixes)

1. The size check ran **only between rounds** (`senior_session.py:217`). A round is up to 25
   calls, and nothing bounded its growth. `agent_node` reads `input_tokens` on every call
   (`splunk_agent.py:729`) but used it only for the output cap.
2. A crashed round **left no trace**: `splunk_subagent.py:319` replaced the round's messages with
   `[]`, and `senior_session.py:157` records size only from finished rounds. The oversized request
   disappeared from every log, so the 70% alert and compaction never fired once in 50 questions.
3. **Clarify calls were never checked** (`splunk_subagent.py:268`): the whole thread plus the
   question was sent, then both were appended.
4. The provider **does not reject an oversized request cleanly**. It stalls and then returns 502,
   so one call could spend up to 4 × the timeout (20 min at 300 s) before failing.

### Decisions

| # | decision | why |
|---|---|---|
| D7 | The check reads the **`input_tokens` the provider already returns** on each reply. No local counting, no extra call. | Zero added latency: one integer comparison per call. The only cost is the summary call when it fires. |
| D8 | Threshold **80% of the window** (`COMPACT_AT = 0.80`, the value already in the code), checked **inside the round after each call**. The between-round projection (`should_compact`) is **deleted**. | Operator's choice. One call adds at most one tool result (at most 12,000 characters) and one reply, so the check after each call catches growth before it compounds. One mechanism, not two. **Open risk:** 204,800 input + the 65,536 output reservation (`token_limit_kwargs`) = 270,336, more than 256K; a reply that used its full reservation at the threshold could overflow. Watch for it in the smoke run. |
| D9 | At the threshold the graph withdraws the tools and asks for `submit_finding` **in the handover template** (the path the iteration cap already uses), with status `context_full`. The session opens a fresh thread seeded with the brief, the handover and the SPL already run, and **continues the same round with the calls it has left**. This does not cost an SH turn or a senior round. | The handover template already carries what a replacement needs. |
| D10 | A crashed round's **messages and size are kept**: on an exception, the thread is read back from the checkpointer instead of replaced with `[]`. | Without this, the next oversized request is invisible again. |
| D11 | Before a clarify call, if the last known size is at or above the threshold, the session hands over first, then asks. | Closes gap 3. |
| D12 | Deadline: **120 s per attempt** (`LLM_TIMEOUT_S`, back from the mid-run 300) and **3 SDK retries** (unchanged), so a timed-out call gives up after at most 4 × 120 s = 8 min, inside the 10-min deadline. | Operator's choice: 300 s did not fix Q328. Its timeouts were oversized requests, which R5 removes. Every one of the 217 rounds recorded on v0.4.5 completed within 120 s per attempt. A timeout discards a reply rather than truncating it; truncation is only the 65,536-token output cap, which is unchanged. |
| D13 | R7 is an **outer retry** around a worker round and an SH call: waits of **30 s, 60 s and 120 s** on a connection error or HTTP 5xx, then the current handling (retire, `RunPaused`). **Timeouts are not retried by R7**: D12 already bounds them, and an oversized request would only stall again. | The SDK's own retries back off for seconds; the v0.4.5 outages lasted minutes (Q328: 502 at 11:24, provider healthy again within minutes). |
| D14 | One helper, `atomic_replace(tmp, dst)`, retries `PermissionError` 5 times with a 0.2 s backoff. All five `os.replace` sites use it: `resume.py`, `sh_memory.py`, `case_file.py`, `splunk_agent.py` (manifest) and `build_manifest.py`. | Fixed once where every caller goes through, not only in the file that crashed (Q311). |

### Invariants

- **I6**: a senior's recorded `input_tokens` never exceeds 80% of its window on the call after a handover, unless the seed alone exceeds it. In that case the round fails with `context_full` rather than looping.
- **I7**: a crashed round's size and messages are in its delegation record.
- **I8**: no API call waits more than 8 min (4 × 120 s, D12) before it is an error.
- **I9**: every `os.replace` in the codebase goes through `atomic_replace`.

### Tests (Claude writes them, red first)

R5: a fake model reporting rising `input_tokens` stops the round at 80%; the next call is on a new
thread whose first message holds the handover; the remaining iterations carry over; a seed already
over the threshold fails with `context_full` rather than looping; a clarify at or above the threshold hands over first; a crashed
round keeps its size. R6: `LLM_TIMEOUT_S == 120` and `LLM_MAX_RETRIES == 3`, so the worst case, `(1 + retries) × timeout`, is at most 600 s. R7: a fake raising
502 twice, then succeeding, is retried with the waits injected (so no real sleeping); a timeout is
not retried by R7; the third failure falls through to today's handling. R8: a replace that raises
`PermissionError` twice, then succeeds, returns normally; a grep test asserts no bare `os.replace`
is left.

**Merge note:** `6d366fd` on `exp/v0.4-conversational` raised `LLM_TIMEOUT_S` to 300; this
branch keeps 120 (D12). At the merge, take this branch's line.
