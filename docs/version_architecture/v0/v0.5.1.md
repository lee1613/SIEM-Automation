# v0.5.1 — Evidence-gated escalation: a refusal produces a package for a human

> **Status: SPEC AGREED WITH THE OPERATOR 2026-10-01. Not built.** No code changes until the operator asks.
> v0.5.0 (reliability) is still in progress; this version builds on it.

## Why this version exists

Today a refusal is a bare end state. SH retires without answering, and the evidence sits in
`questions/<QID>.json`, `timeline.md` and `premise_ledgers/<QID>.json`, but nothing assembles it for
a reader. In v0.4.5, 22 of 50 questions ended this way, and 8 of them had held the exact official
answer. A person picking one up has to reconstruct the case from three logs.

The existing `hitl` module is not this: it pauses a run on a provider failure (`RunPaused`,
`decision_request.json`) and is about infrastructure, not evidence.

The goal is the README's claim made true: a production-grade agentic system whose decisions are
reliable, consistent and interpretable, with a human-in-the-loop escalation path when the evidence
is not there.

## Requirements (operator, 2026-10-01)

| # | requirement |
|---|---|
| E1 | When SH ends a question **without a submitted answer**, the runner writes an **escalation package** for that question and the run continues with the next question. |
| E2 | Triggers: **(a)** SH declines on purpose, **(b)** the run hits its caps with no answer, **(c)** a runner gate blocks the submission (for example R4, a load-bearing premise UNVERIFIED or REFUTED). Provider failures (`RunPaused`) are **not** triggers. |
| E3 | The package is **assembled by code** from existing state. SH contributes exactly one free-text field, `what_would_settle_it`. |
| E4 | Writing the package must **never change the run**: best-effort, a failure logs a warning and nothing else. No change to SH's decision path, the gates, the budgets or the order of questions. |
| E5 | **Nothing is auto-submitted.** `best_candidate` is for the human reviewer only. Scoring stays the exact-match rule, so scores stay comparable across versions. |
| E6 | Result docs and the README report three outcomes: **correct / wrong submitted / escalated**. |

## Decisions

| # | decision | why |
|---|---|---|
| D1 | Code assembles the package; one SH field only. | Code-assembled facts cannot be hallucinated or omitted, and every claim traces to a log. A prose summary by SH costs an extra call on a failed question and can contradict the ledger. |
| D2 | One file per escalated question: `escalations/<QID>.json` in the run folder. | No new top-level folder (repo layout rule). |
| D3 | `run_summary.json` gets `escalated: [{id, trigger}]`; `timeline.md` gets one line where it happened. | A reader sees escalations without opening each file. |
| D4 | No scoring credit for a good escalation. | It would change the scoring rule and break comparability with every earlier version. Revisit separately. |

## Package fields

| Field | Source |
|---|---|
| `question_id`, `question_text` | runner |
| `trigger` (`declined` / `caps` / `gate`) and `gate_reason` | runner; `gate_reason` names the failed step (for example R4) |
| `best_candidate`, `confidence` (nullable) | last finding or SH draft |
| `premises` (id, status, load-bearing) | premise ledger |
| `evidence` (SPL run, result excerpts, log paths) | senior logs |
| `blocking_gap` | code, from the UNVERIFIED and REFUTED load-bearing premises |
| `what_would_settle_it` | SH, one field |
| `cost_so_far` | usage tracker |

## Invariants (each gets a test)

- **I1** — an escalation never changes what is submitted to `LocalScoreboard`.
- **I2** — a package is written for every question that ends unanswered by a, b or c, and for no
  question that was answered or ended on `RunPaused`.
- **I3** — a failure while assembling or writing a package leaves the run, the next question and
  `run_summary.json` untouched apart from a logged warning.
- **I4** — every evidence entry in a package names a file that exists in the run folder.

## Out of scope

Scoring credit for escalations (D4); a UI or queue for reviewers; changing when SH decides to
refuse. Those are separate decisions.

## To confirm when it is built

Where SH's no-answer end states converge in `sh_loop.py` (the three triggers may leave through
different paths), and whether `premise_ledgers/<QID>.json` and the senior logs already carry every
package field. Both are read-only checks before any code.
