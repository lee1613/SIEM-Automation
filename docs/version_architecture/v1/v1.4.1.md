# SIEM Agent v1.4.1 — Conversational loop, post-smoke hardening (IN PROGRESS)

**Status:** Q216 smoke-tested 2026-09-18 (wrong, 3564; see below). No full run. v1.4.1 is v1.4.0 (see
[`v1.4.0.md`](v1.4.0.md)) plus what the 2026-09-18 GLM-5.3 five-question smoke test and the
Q216 threat-hunter review taught us. The architecture is unchanged: the same six routes,
the same question-scoped seniors, the same tier table.

---

## What changed vs v1.4.0

| Area | v1.4.0 (smoke-tested) | v1.4.1 |
|---|---|---|
| Technique tags on SPAWN | `hunter` / `content` / `metrics` | `metrics` or plain senior; `hunter` and `content` pruned (SH's directives already carried them) |
| Budget ran out without an SH ANSWER | a senior's value was submitted anyway | honest marker `SH retired without answering` — only SH answers |
| Rubric | R1 scope, R2 progress, R3 readiness | + **R4 premise verification**, a warning and never a gate |
| Unverified premises | not tracked | report has `## Assumptions`; each UNVERIFIED line is flagged to SH, and the senior's next directive opens with "verify these first" |
| Senior's open questions | could be ignored | SH must answer every one (`open_question_answers`, enforced); answers reach the senior with its next directive |
| SH as reviewer | router | reads each report as a senior threat hunter reviewing a junior's work |
| Rounds | per question (waves): a 2nd senior only got what the 1st left | **per senior**: each senior gets the full tier rounds; the question ends on rounds only when every slot is spent and nobody has rounds left |
| Parallel seniors | allowed freely | only with a competing suspicion and **disjoint sourcetype/source scopes** (runner rejects overlap) |
| Iterations per round | 8. The 1000-pt ceiling of 3×8×8 = 192 was reachable only with 3 seniors in parallel in every one of the question's 8 waves; one senior at a time topped out at 8×8 = 64 | **12**. The ceiling is 3×8×12 = 288, reachable one after another too, because rounds are per senior |
| SH turns (1000 / 500 / 100 pt) | 12 / 8 / 5 | **28 / 13 / 5**: `seniors × (rounds + 1) + 1`, so seniors running one after another can each use all their rounds |

**Why each one.**
- *Honest fallback:* the loop's score has to mean SH judged the answer.
- *R4 and open questions:* in the Q216 review, the senior picked the wrong entity on a premise
  it never tested.
- *Soft R4:* sometimes an educated guess is the only move. Blocking it would turn a near miss
  into a guaranteed miss, so the loop warns loudly instead.
- *Per-senior rounds:* the old wave clock made the second senior's budget depend on the first
  senior's.
- *12 iterations:* in the v1.4.0 GLM transcripts, **17 of 22 senior reports (77%) hit the
  8/8 iteration cap**, meaning they were cut off rather than finished. 7 of SH's 13 COMMANDs
  were `continue`: the same work, carried on in the next round. A longer round lets that work
  finish inside one round instead of being split across two.
- *Same-scope successors are intended.* When a senior's rounds run out, SH may spawn a
  successor on the same sourcetype/source to carry the work on. Nothing blocks this, which
  lets one line of investigation run for up to 3 × 8 rounds. Only seniors running at the same
  time must not overlap.
- *More SH turns:* with rounds per senior, 12 turns could not cover 3 seniors × 8 rounds run
  one after another.

## Smoke test — Q216, 2026-09-18

Run `v1.4.1_glm-5.3_Q216_r2` on commit `9d6c4ed`: GLM-5.3 senior, gpt-5.4 SH. The first
attempt, `v1.4.1_glm-5.3_Q216`, stopped on the runaway cap (see the changelog).

| | |
|---|---|
| Answer | **3564**, wrong (official 1666); grounded |
| Path | 1 senior, 2 rounds (12 + 8 iterations, round 1 cut off at the cap), 3 SH turns, 20/288 iterations |
| Cost | $1.00 (SH $0.04 / senior $0.96), tracker-priced |
| Latency | 28 min |

**What worked.**
- The window-sized cap held: round 2 ran to the senior's own finish with no runaway.
- R4 did its job inside the senior's frame. Round 1 filed its candidate with its premises
  marked UNVERIFIED. SH answered both open questions and commanded a same-session test.
  Round 2 verified every listed premise with a query.

**What failed: the entity was never a listed premise.**
- The senior searched the keyword `monero` (0 hits), then stratum ports. It found the feed's
  only port-3333 flow (powershell on 192.168.70.186 → 45.77.53.176) and built everything on
  that host.
- "The Monero-generating endpoint is the host with a stratum flow" was never written as an
  assumption, so R4 never tested it. Every verified premise sat downstream of that choice.
- The Coinhive browser miner on 192.168.247.131 (the `dh` field is the flow's destination
  domain name, and the review found `dh=*coinhive*` there) was never searched. The field was
  even in SH's round-2 scope.
- SH accepted 3564 over the senior's alternate, 112, without asking whether another
  endpoint could fit the question's words.

This is the same wrong-entity failure the threat-hunter review found in v1.4.0, now with
stronger verification of the wrong entity.

## Changelog — EXPERIMENT

- **EXPERIMENT** — Pruned the `hunter` and `content` techniques from the conversational loop,
  on the smoke-run evidence above. `conversation.TECHNIQUES` is now `("metrics",)` and SPAWN's
  `technique` is `Literal["metrics", ""]`. A senior SPAWN no longer requires a technique: empty
  means a plain senior. That empty value used to fall back to `"hunter"` in `sh_loop` and
  `SeniorSession`, which would have quietly re-injected the pruned prompt. It now maps to the
  role `"senior"`, which has no `SPECIALISTS` entry, so the graph gets `FINISH_INSTRUCTIONS`
  only. `pool.run_round`/`clarify` default to `"senior"` too. The SH brief asks "whether it is a
  metrics senior" instead of "its technique". `specialists.py` is untouched, because the
  compiler A/B control still uses all three. 3 new tests (hunter/content rejected, plain spawn
  valid, empty technique → `"senior"` graph); the existing SPAWN fixtures moved from `hunter` to
  `""`. Suite 433 passed / 5 skipped.
- **EXPERIMENT** — **Only SH answers.** When a question ends without an accepted SH ANSWER
  (`rounds`, `turns` or `ungrounded`), `run_question` now returns
  `sh_loop.NO_ANSWER = "SH retired without answering"` instead of ranking senior values and
  submitting the best one. The old fallback bypassed SH's own decision. In Q217
  (`test_20260918_113209`) SH retired its last senior "rather than force an unsupported
  answer", and the loop then submitted `pwned.jpg`, a filename, for a question asking for a
  chart type. The R1 exclusion (M4) could not stop it, because no report was graded R1 FAIL.
  The ungrounded case follows the same rule: after two of SH's values fail grounding, the loop
  no longer submits a third value SH never proposed. `end_reason` still says which budget or
  gate ended the question. The marker passes `answer_shaped`, so the runner records and submits
  it (it scores wrong, which is the honest result), and `--hints` still fires because the marker
  is never grounded. The M3/M4 ranking code is deleted. 1 new test (the Q217 case) and 3
  rewritten (they asserted the removed behaviour). Suite 433 passed / 5 skipped.
- **EXPERIMENT** — **R4 premise verification, open-question enforcement, and a reviewer
  persona**, all from the Q216 post-mortem. A blind threat-hunter review of Q216's transcript
  found the senior had *assumed* "powershell is the miner", never tested it, and built every
  later query on it. SH then accepted the report while ignoring both of the senior's open
  questions. By user decision, and generalising the lesson rather than fitting a Q216-specific
  rule:
  (1) **R4 premise verification**, a fourth graded dimension (`r4_premise_verification`): is
  every premise the conclusion or direction rests on backed by a result shown in the report?
  **R4 = FAIL blocks ANSWER** (`conversation.premise_blocked`), alongside R1. Grade rows and
  `grade_report.py` carry `r4`.
  (2) The report template gains **`## Assumptions`**: each premise tagged VERIFIED (with the
  query and the result) or UNVERIFIED. This is what makes R4 gradable by an SH that cannot
  query Splunk.
  (3) The senior brief now tells seniors about R4. This departs from the spec's "the senior
  never sees the rubric", by user decision. It also carries a "no untested assumptions" rule
  with generic examples (no dataset facts, nothing tied to a specific question, to avoid
  leakage), plus a NOT_FOUND rule: when a round finds nothing, the next round starts by
  testing the UNVERIFIED premises.
  (4) **SH must answer every open question.** A new `open_question_answers` field;
  `conversation.open_question_violations` rejects a turn whose route to a senior (or whose
  ANSWER built on its report) answers fewer questions than `senior_report.open_questions()`
  counted ("none" bullets don't count). The answers reach the senior at the head of its next
  COMMAND/CRITIC directive, or as a `preface` on a CLARIFY, and are logged in
  `conversation.md`.
  (5) **A reviewer persona in the SH prompt:** SH reads each report as a senior threat hunter
  reviewing a junior. It checks each assumption against the queries run, looks for results that
  were explained away, checks the candidate's shape against the question's words, and acts on a
  flaw with CRITIC or a premise-testing COMMAND. This is meant to prompt careful review (and
  CRITIC use, which was 0 of 22 in the smoke test) through judgement rather than a new rule.
  Considered and rejected: "search named indicators before volume". It fits Q216 but not
  threat hunting in general, and (1) covers the failure more generally.
  New tests: open-question parsing (5), R4/premise gate and open-question gate units (8), loop
  tests for a rejected unanswered turn with answer delivery and for R4 in grade rows (2).
  Fixtures gained the two new fields. Suite 448 passed / 5 skipped. The in-flight
  `v1.3.1_gpt-5.4-mini` run started before this change and runs on the prior code.
- **EXPERIMENT** — Per-senior rounds, parallel seniors under a no-overlap rule, soft R4,
  12 iterations per round. Five changes, made after the `gpt-5.4-mini` A/B finished:
  (1) **Rounds are per senior, not per question.** The old wave clock capped the whole
  question at `rounds` waves, so a second senior only got what the first one left.
  `QuestionState.exhausted()` now returns "rounds" only when every spawn slot is used AND no
  active senior has rounds left. Waves are still counted but cap nothing. `slots_remaining`
  replaces `waves_remaining`, and each senior is granted the full tier `rounds`.
  (2) **A second senior in parallel only under the PARALLEL SENIORS rule** in the SH prompt:
  SH has a competing suspicion, and the two scopes share no sourcetype/source. The reason is
  stated in `reason`. `conversation.spawn_overlap_violations` enforces the scope part. When a
  turn would leave two or more seniors running, every new senior SPAWN must name a
  sourcetype/source disjoint from each other running scope. An unscoped running senior blocks a
  parallel spawn. Exploration spawns and any turn carrying an ANSWER are exempt (entries after
  an ANSWER are ignored per M7).
  (3) **R4 is soft.** `premise_blocked` was removed, so R4 = FAIL no longer blocks ANSWER. An
  educated guess is allowed. A FAIL-graded ANSWER is logged as "answered on an unverified
  premise … dangerous ground". Instead: the wave message flags "N UNVERIFIED premise(s)" per
  report (`senior_report.unverified_premises`), and a WEAK/FAIL R4 prepends "FIRST … verify the
  UNVERIFIED premises" to the next directive.
  (4) **The senior brief has no examples.** The premise section says what to verify, not which
  premises. Examples had risked leaking a question's shape.
  (5) **`ROUND_ITERS` 8 → 12.** Prompts read it through f-strings. The 1000-pt ceiling is now
  3 seniors × 8 rounds × 12 = 288 iterations.
  Tests updated for per-senior rounds and the 12-iteration cap. New tests cover soft R4, the
  overlap gate and the unverified-premise count. Suite 462 passed / 5 skipped.
  **Not changed, flagged:** the SH turn caps (5/8/12) can bind before per-senior rounds when
  seniors run one after another.

- **GENERAL** — Runaway cap sized to the context window, per round. The first v1.4.1 Q216
  smoke run (`v1.4.1_glm-5.3_Q216`, 2026-09-18) stopped with no answer.
  - **Cause:** 7 steps into round 2, the GLM-5.3 senior had produced 113,542 output tokens
    (about 16K per call, reasoning included). That passed the flat `OUTPUT_TOKEN_CAP =
    100_000`, which was calibrated on one-shot workers producing about 11–12K over their
    whole life. The counter already reset every round, so this was one round, not an
    accumulation.
  - **Change:** `splunk_agent.round_output_cap()` now sets each round's cap to the context
    window minus the prompt size at the round's first call (256K − starting context for
    GLM). It is stored in the new `AgentState.output_cap`. A graph built without a window
    keeps the flat 100K. `over_output_cap()` is the one check the router and
    `splunk_subagent` both use.
  - **Scope:** `SplunkWorkerPool` passes `context_window(senior_model)`, so the compiler
    loop's workers get the window cap too.
  - New `test_output_cap.py` (4 tests).
- **EXPERIMENT** — A runaway no longer pauses the run in the conversational loop.
  - **Old behaviour:** the HITL pause (v1.3.0, `hitl.py`, 2026-09-04) exists for provider
    outages, where SH replanning would only send more workers at a dead endpoint. v1.3.0
    also routed runaways to it, because back then a runaway meant a stuck one-shot worker.
  - **Why it's wrong here:** in the conversational loop, the runaway is already handled.
    The senior is retired with a handoff, its slot is refunded and SH decides whether to
    respawn. The pause instead stopped the whole detached run, and mislabelled the event
    "API FAILURE via api.featherless.ai", quoting the senior's own output as the error.
  - **Change:** `sh_loop` now calls the HITL pause only for `api_failed`. The compiler
    loop's `executor_graph` is unchanged: it still pauses on both, as the A/B control.
  - Two new loop tests. Suite 498 passed / 5 skipped.
