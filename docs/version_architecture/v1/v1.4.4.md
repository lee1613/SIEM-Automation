# v1.4.4 — soundness, not just citation

**In progress.** Opened 2026-09-22, out of the root-cause analysis of
`log/temp/v1.4.3_stamp_smoke5_r1` (2/5) read against
`log/v1/v1.4/v1.4.1_glm-5.3_smoke5_r1` (also 2/5).

## Why this version exists

The two runs scored identically on the same five questions, failed the same three, and
put the **same wrong value on Q216** (`112`, official `1666`). Everything v1.4.2 and
v1.4.3 added between them — the premise ledger, the stamp, the false-stamp trigger, the
blind validator, the alternative agent — changed the score by zero. That is the finding
this version starts from: the machinery is not wrong, it is aimed at the wrong question.

Four mechanisms were implicated, and each has one change below.

## Changelog

### 1. The stamp obligation arrived after the turn it applied to

`stamp_violations()` computes the set of premises SH owes a stamp on, and uses it to
build a rejection. The same set is fully knowable **before** the turn — the runner holds
the ledger — and SH was never told it there. The per-turn instruction in `render_wave`
said "grade it, answer every open question, emit one route per senior" and did not
mention stamping at all; the obligation lived only in the system prompt, ~100 lines away
from the instruction block it applied to.

The cost is not abstract. A rejected turn is not given back (`render_rejection` says so
in as many words), so each of these burned a turn from the question's budget. Across the
five questions, 8 turns were spent re-issuing a turn whose only fault was a missing stamp.

**Change** (`sh_loop.render_wave`): when `ledger.unstamped()` is non-empty, the wave
opens its instruction block with `STAMP FIRST — <ids> …`, naming the exact premise ids
and both questions. Nothing is asked for after the fact that could have been asked for
before it.

### 2. The stamp asked about the citation, never about the claim

The stamp asked one question: *does this quote establish this claim as written?* That is
**validity**. It does not ask whether the claim is **true**.

Q216 is the whole argument. Its selection premise —

> *"192.168.70.186 is the endpoint because it alone holds the sole pool-port (3333)
> flow… Rival 192.168.247.131's mining traffic is coinhive browser cryptojacking over
> 443 by chrome.exe (a browser page, not an endpoint miner, no pool port)"*

— was cited with genuine, verbatim, correctly-read rows. It passed the stamp. It passed
again after a retirement, again under an alternative agent: five times in total. And it
is false. CoinHive *is* an in-browser Monero miner, the endpoint the question meant is
`192.168.247.131` (BudStoll), and that host sits **two rows below the chosen one in the
same result table**. An argument can be valid and unsound; the stamp tested only
validity, so a flawlessly-evidenced claim about the wrong endpoint had nothing to fail.

**Change** (`conversation.PremiseStamp`): a second, separate pair of fields.

| field | question | catches |
|---|---|---|
| `establishes` + `reason` | **validity** — does the quote support the claim *as written*? | a quote that walks past a limit the claim states about itself |
| `claim_holds` + `holds_reason` | **soundness** — is the claim *right* about this question? | a claim cited flawlessly about the wrong entity, feed, or reading |

`holds_reason` must name the strongest rival reading the evidence rules out; a blank one
is a gate violation. Either field being false fires the existing machinery — retire the
senior, spawn a validator — through the new `conversation.stamp_is_false()`, so nothing
downstream had to learn about the second question. The ledger keeps both readings
separately (`Premise.stamp_holds`, `Premise.holds_reason`, both emitted into
`premise_ledger.json`): collapsing them at write time would make the post-run reading
that motivated this — *how often is a claim validly cited and still wrong* — unanswerable
from the one artifact that outlives the run.

### 3. The validator re-checked the incumbent, which is a confirmation frame

The validator was handed the claim and the evidence offered for it, and asked whether the
evidence holds. Blind, disinterested — and pointed at the wrong target. On Q216 the
incumbent was re-examined round after round and passed every time, while **nobody was
ever sent to make the CoinHive host's case**. A reader asked "does this hold?" is doing a
different job from one asked "go and make the other one true."

**Change** (`validator.brief_for_rival`, `rival_mode`, `as_rival_verdict`): when the
nominated premise is a `selection` premise with a named `rival` — and `PremiseLedger.add`
already *refuses* a selection premise with an empty `rival`, so the text is always there —
the validator is handed **the rival's words as the claim to settle**, blind, with no quote
and no mention of the incumbent. This is proof by contradiction (reductio ad absurdum) in
shape: assume the strongest not-X and go looking for what would make it true.

The verdict mapping is deliberately asymmetric, and that asymmetry is the safety property:

- rival **VERIFIED** → the incumbent selection is **REFUTED**. Something fitting the
  question at least as well has been stood up from data.
- rival **REFUTED / UNVERIFIED / no verdict** → the incumbent is **left exactly where it
  was**, and SH is told so in those words.

The second case is not a confirmation, and the code says why: *no evidence for the rival
is not evidence for the incumbent* — reading it as proof is the argument from ignorance.
The test can only ever take a claim down, never prop one up, so a lazy or unlucky
validator cannot manufacture support for whatever SH already believed.

Coverage premises, and any premise with no rival, keep the original brief unchanged.

### 4. "The value cannot be read" had no way to be said

Q217 and Q329 both ended `SH retired without answering`. Both are, per the official
BOTSv3 hints, decode-base64-and-**look-at-the-image** questions:

> Q217 hint 3 / Q329 hint 3: *"You will need to find a site to decode the base64 to a
> viewable image. CyberChef is a good one!"*

On Q217 a senior located `image001.jpg` in the right thread and stated plainly that the
answer *"lives only in the image pixels."* SH treated that as a scope problem and spent a
third senior and four rounds searching `osquery`, `Sysmon`, `WinEventLog` and
`stream:http` for a file that never touched a disk — s3 then proved it appears in **zero
events** across all four. Roughly half of each question's budget went on hunting after the
hunt was provably over.

**Change** (`conversation.unanswerable_violations`): an ANSWER may carry
`value_kind="not_answerable"` with `value="NOT_ANSWERABLE"` — a fixed sentinel, so no
free-text guess can reach the scoreboard — and the runner submits blank
(`sh_conv_unanswerable` in the event log).

**There is no new route and no new trust.** SH grades R4 PASS on the turn it wants to
answer, every time, across three runs and six seniors. A cheap exit would be taken early,
and "unanswerable" is the most attractive exit ever offered to it, because nothing can
contradict it. So this is an ANSWER whose value happens to be a capability verdict, and it
must rest on a load-bearing premise that **a senior** verified against a quote from output
that senior actually received, and that SH then stamped true. SH verifies nothing itself.
It therefore cannot reach this conclusion by asserting it — only by having sent someone to
find the artifact and come back with the wall in a quote. It still scores zero; what it
buys is the seniors that would otherwise go on proving a negative, and a run record that
separates *could not hunt* from *could not read*.

### 5. The premise ledger did not survive the process that wrote it

Q216's and Q217's premises are **gone** from the v1.4.3 run. Three distinct faults, all in
the persistence path:

1. `dump_ledgers` ran **once, at the end of `main()`, outside any `try/finally`**. The
   HITL gate raised `RunPaused`, `main()` unwound, and every ledger the process held went
   with it. This is what actually destroyed Q216 and Q217.
2. A resumed process starts `ledgers: dict = {}` and has no seed step, so it cannot
   re-derive an earlier segment's premises. Every *other* artifact is rehydrated on
   resume — `results` from `questions/<qid>.json`, points, `failed_delegations`,
   `tracker.seed(...)`, `metrics_rows`, the file-backed case file and scoreboard. The
   ledger was the single exception.
3. The dump was one whole-file overwrite, which turns fault 2 from lossy into destructive.

**Change** (`premise.dump_question_ledger`, `premise.ledger_dir`, and
`dump_ledgers(..., run_dir=)`): each question's ledger is written to
`premise_ledgers/<QID>.json` **the moment that question ends**, beside the existing
`metrics.json` write. The merged `premise_ledger.json` is rebuilt by reading that
directory, so a resumed run's merged view gains the earlier segment instead of replacing
it. All three faults close with one change: a file written at question end cannot be lost
by an exception later, and a file named for one question cannot be overwritten by another.

## Verification

- `pytest agent/v1/tests/` — **668 passed, 5 skipped** (652 before; 16 new in
  `agent/v1/tests/test_v144_soundness.py`).
- `ruff check` clean on every changed file.
- The 23 existing `PremiseStamp(...)` constructions in `test_stamp.py` and
  `test_sh_loop.py` gained `claim_holds=True`, preserving their original semantics
  exactly: every one of them asserts on `establishes`.

## What this version does NOT do

- **It does not make Q217 or Q329 answerable.** Both need base64 → image → visual
  reading, and nothing here adds that. Change 4 stops the system wasting seniors on them;
  it does not score them. The capability question is open and tracked separately.
- **It does not change how the AA is spawned.** The alternative agent's brief is still
  SH's own prose (`reason`, `deviation`, `inherited_entities`) plus the runner's refuted
  block — and that block is empty unless something is `REFUTED`, which only a validator
  can produce. So on a false stamp *with no refutation*, the AA receives nothing the
  runner enforced, and the spec's "AA scoped by the false stamp's reason" is not what the
  code does: `stamp_reason` is never injected into `_spawn_directive`. Recorded as a known
  gap rather than patched blind.
- **It does not address Q216's second error.** Even with the right endpoint the system
  would have answered `1758` (sum of flow durations) where the official method, per hint
  3, is the span from first to last communication — `max(fes) - min(fss)` = `1666`. The
  senior noticed the flows overlap and used that as grounds to *dismiss* the candidate,
  when overlap is precisely why the span is the right arithmetic.
