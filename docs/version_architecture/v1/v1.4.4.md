# v1.4.4 — soundness, not just citation

**In progress.** Opened 2026-09-22, out of the root-cause analysis of
`log/temp/v1.4.3_stamp_smoke5_r1` (2/5) read against
`log/v1/v1.4/v1.4.1_glm-5.3_smoke5_r1` (also 2/5).

## Why this version exists

The two runs scored identically on the same five questions, failed the same three, and
put the **same wrong value on Q216** (`112`, official `1666`). Everything v1.4.2 and
v1.4.3 added between them — the premise ledger, the stamp, the false-stamp trigger, the
blind validator, the alternative agent — changed the score by zero. That is the finding
this version starts from: the machinery is not wrong, it is aimed at the wrong question.

Four mechanisms were implicated, and each has one change below.

## Changelog

### 1. The stamp obligation arrived after the turn it applied to

`stamp_violations()` computes the set of premises SH owes a stamp on, and uses it to
build a rejection. The same set is fully knowable **before** the turn — the runner holds
the ledger — and SH was never told it there. The per-turn instruction in `render_wave`
said "grade it, answer every open question, emit one route per senior" and did not
mention stamping at all; the obligation lived only in the system prompt, ~100 lines away
from the instruction block it applied to.

The cost is not abstract. A rejected turn is not given back (`render_rejection` says so
in as many words), so each of these burned a turn from the question's budget. The run
lost **30 turns to rejections across five questions**, and the two largest reasons are
the same bug:

| rejection reason | turns | Q216 | Q217 | Q224 | Q328 | Q329 |
|---|---|---|---|---|---|---|
| open questions unanswered | **17** | 2 | 6 | 4 | 3 | 2 |
| unstamped — "you have not read them" | **11** | 3 | 1 | 4 | 2 | 1 |
| ANSWER blocked by ledger | 3 | 2 | 0 | 1 | 0 | 0 |
| R4 above its ceiling | 3 | 1 | 0 | 0 | 1 | 1 |
| premise re-filed / refused | 2 | 1 | 0 | 1 | 0 | 0 |
| stamp re-sent for a stamped premise | 2 | 1 | 0 | 1 | 0 | 0 |
| routed at a retired senior | 1 | 0 | 0 | 1 | 0 | 0 |

28 of 30 rejections are a requirement the runner could state **before** the turn and was
stating only **after** it. `open_question_violations` reads
`ledger.open_questions_for(sid)`; `stamp_violations` reads `ledger.unstamped()`. Both
lists exist at render time.

**Change** (`sh_loop.render_wave`): when `ledger.unstamped()` is non-empty the wave opens
its instruction block with `STAMP FIRST — <ids> …`, naming the exact premise ids and both
questions; when any senior in the wave has open questions it adds `ANSWER BY ID — s1 asks
q3, q4 …`. Nothing is asked for after the fact that could have been asked for before it.

### 2. The stamp asked about the citation, never about the claim

The stamp asked one question: *does this quote establish this claim as written?* That is
**validity**. It does not ask whether the claim is **true**.

Q216 is the whole argument. Its selection premise —

> *"192.168.70.186 is the endpoint because it alone holds the sole pool-port (3333)
> flow… Rival 192.168.247.131's mining traffic is coinhive browser cryptojacking over
> 443 by chrome.exe (a browser page, not an endpoint miner, no pool port)"*

— was cited with genuine, verbatim, correctly-read rows. It passed the stamp. It passed
again after a retirement, again under an alternative agent: five times in total. And it
is false. CoinHive *is* an in-browser Monero miner, the endpoint the question meant is
`192.168.247.131` (BudStoll), and that host sits **two rows below the chosen one in the
same result table**. An argument can be valid and unsound; the stamp tested only
validity, so a flawlessly-evidenced claim about the wrong endpoint had nothing to fail.

**Change** (`conversation.PremiseStamp`): a second, separate pair of fields.

| field | question | catches |
|---|---|---|
| `establishes` + `reason` | **validity** — does the quote support the claim *as written*? | a quote that walks past a limit the claim states about itself |
| `claim_holds` + `holds_reason` | **soundness** — is the claim *right* about this question? | a claim cited flawlessly about the wrong entity, feed, or reading |

`holds_reason` must name the strongest rival reading the evidence rules out; a blank one
is a gate violation. Either field being false fires the existing machinery — retire the
senior, spawn a validator — through the new `conversation.stamp_is_false()`, so nothing
downstream had to learn about the second question. The ledger keeps both readings
separately (`Premise.stamp_holds`, `Premise.holds_reason`, both emitted into
`premise_ledger.json`): collapsing them at write time would make the post-run reading
that motivated this — *how often is a claim validly cited and still wrong* — unanswerable
from the one artifact that outlives the run.

### 3. The validator re-checked the incumbent, which is a confirmation frame

The validator was handed the claim and the evidence offered for it, and asked whether the
evidence holds. Blind, disinterested — and pointed at the wrong target. On Q216 the
incumbent was re-examined round after round and passed every time, while **nobody was
ever sent to make the CoinHive host's case**. A reader asked "does this hold?" is doing a
different job from one asked "go and make the other one true."

**Change** (`validator.brief_for_rival`, `rival_mode`, `as_rival_verdict`): when the
nominated premise is a `selection` premise with a named `rival` — and `PremiseLedger.add`
already *refuses* a selection premise with an empty `rival`, so the text is always there —
the validator is handed **the rival's words as the claim to settle**, blind, with no quote
and no mention of the incumbent. This is proof by contradiction (reductio ad absurdum) in
shape: assume the strongest not-X and go looking for what would make it true.

The verdict mapping is deliberately asymmetric, and that asymmetry is the safety property:

- rival **VERIFIED** → the incumbent selection is **REFUTED**. Something fitting the
  question at least as well has been stood up from data.
- rival **REFUTED / UNVERIFIED / no verdict** → the incumbent is **left exactly where it
  was**, and SH is told so in those words.

The second case is not a confirmation, and the code says why: *no evidence for the rival
is not evidence for the incumbent* — reading it as proof is the argument from ignorance.
The test can only ever take a claim down, never prop one up, so a lazy or unlucky
validator cannot manufacture support for whatever SH already believed.

Coverage premises, and any premise with no rival, keep the original brief unchanged.

### 4. "The value cannot be read" had no way to be said

Q217 and Q329 both ended `SH retired without answering`. Both are, per the official
BOTSv3 hints, decode-base64-and-**look-at-the-image** questions:

> Q217 hint 3 / Q329 hint 3: *"You will need to find a site to decode the base64 to a
> viewable image. CyberChef is a good one!"*

On Q217 a senior located `image001.jpg` in the right thread and stated plainly that the
answer *"lives only in the image pixels."* SH treated that as a scope problem and spent a
third senior and four rounds searching `osquery`, `Sysmon`, `WinEventLog` and
`stream:http` for a file that never touched a disk — s3 then proved it appears in **zero
events** across all four. Roughly half of each question's budget went on hunting after the
hunt was provably over.

**Change** (`conversation.unanswerable_violations`): an ANSWER may carry
`value_kind="not_answerable"` with `value="NOT_ANSWERABLE"` — a fixed sentinel, so no
free-text guess can reach the scoreboard — and the runner submits blank
(`sh_conv_unanswerable` in the event log).

**There is no new route and no new trust.** SH grades R4 PASS on the turn it wants to
answer, every time, across three runs and six seniors. A cheap exit would be taken early,
and "unanswerable" is the most attractive exit ever offered to it, because nothing can
contradict it. So this is an ANSWER whose value happens to be a capability verdict, and it
must rest on a load-bearing premise that **a senior** verified against a quote from output
that senior actually received, and that SH then stamped true. SH verifies nothing itself.
It therefore cannot reach this conclusion by asserting it — only by having sent someone to
find the artifact and come back with the wall in a quote. It still scores zero; what it
buys is the seniors that would otherwise go on proving a negative, and a run record that
separates *could not hunt* from *could not read*.

### 5. The premise ledger did not survive the process that wrote it

Q216's and Q217's premises are **gone** from the v1.4.3 run. Three distinct faults, all in
the persistence path:

1. `dump_ledgers` ran **once, at the end of `main()`, outside any `try/finally`**. The
   HITL gate raised `RunPaused`, `main()` unwound, and every ledger the process held went
   with it. This is what actually destroyed Q216 and Q217.
2. A resumed process starts `ledgers: dict = {}` and has no seed step, so it cannot
   re-derive an earlier segment's premises. Every *other* artifact is rehydrated on
   resume — `results` from `questions/<qid>.json`, points, `failed_delegations`,
   `tracker.seed(...)`, `metrics_rows`, the file-backed case file and scoreboard. The
   ledger was the single exception.
3. The dump was one whole-file overwrite, which turns fault 2 from lossy into destructive.

**Change** (`premise.dump_question_ledger`, `premise.ledger_dir`, and
`dump_ledgers(..., run_dir=)`): each question's ledger is written to
`premise_ledgers/<QID>.json` **the moment that question ends**, beside the existing
`metrics.json` write. The merged `premise_ledger.json` is rebuilt by reading that
directory, so a resumed run's merged view gains the earlier segment instead of replacing
it. All three faults close with one change: a file written at question end cannot be lost
by an exception later, and a file named for one question cannot be overwritten by another.

- `ruff check` clean on every changed file.

## What this version does NOT do

- **It does not make Q217 or Q329 answerable.** Both need base64 → image → visual
  reading, and nothing here adds that. Change 4 stops the system wasting seniors on them;
  it does not score them. The capability question is open and tracked separately.
- **It does not change how the AA is spawned.** The alternative agent's brief is still
  SH's own prose (`reason`, `deviation`, `inherited_entities`) plus the runner's refuted
  block — and that block is empty unless something is `REFUTED`, which only a validator
  can produce. So on a false stamp *with no refutation*, the AA receives nothing the
  runner enforced, and the spec's "AA scoped by the false stamp's reason" is not what the
  code does: `stamp_reason` is never injected into `_spawn_directive`. Recorded as a known
  gap rather than patched blind.
- **It does not address Q216's second error.** Even with the right endpoint the system
  would have answered `1758` (sum of flow durations) where the official method, per hint
  3, is the span from first to last communication — `max(fes) - min(fss)` = `1666`. The
  senior noticed the flows overlap and used that as grounds to *dismiss* the candidate,
  when overlap is precisely why the span is the right arithmetic.

### 6. The SH prompt is now a numbered procedure

The prompt was a set of well-argued topic sections with no stated order of operations.
SH had to infer, every turn, which obligation came first — and it inferred wrong: 28 of
30 rejected turns were a missing stamp or a missing open-question answer.

`SH_SYSTEM_PROMPT` is now an explicit SOP: **STAGE A** (a question arrives: fix the
entity / act / measure), **B** (spawning), **C1–C8** (a wave comes back), **D** (route
choice, first-match list), **E** (retire + replace), **F** (answering), **G** (the
unanswerable path), then a REFERENCE block holding the material that is looked up rather
than followed in order.

The ordering inside STAGE C is load-bearing, not cosmetic:

| step | why here |
|---|---|
| C1 read the whole wave | a sibling report often answers another's open question |
| C2 read the ledger | the premise SH is about to file is usually already in it |
| **C3 stamp** | **before routing** — a false stamp retires the senior, and a COMMAND aimed at a senior SH's own stamp just retired is itself a rejected turn (it happened on Q224) |
| C4 nominate | only when a stamp was false |
| C5 answer open questions | the largest single rejection cause |
| C6 grade | after C3, because the stamps set the R4 ceiling |
| C7 file premises, choose route | premises must be filed while a senior still has rounds |
| C8 emit | |

C4 also settles an ambiguity that was never stated anywhere: **SH does not spawn the
validator.** The runner retires the senior and runs the validator on the nominated
premise, automatically. SH only names the premise. Left implicit, this invited SH either
to burn a SPAWN slot on a validator it cannot spawn, or to avoid stamping false at all
for fear of the cost.

C3 also states the validity/soundness distinction in full, with the Q216 case as the
worked example, rather than leaving it in the field descriptions.

### 7. The alternative agent is briefed on what was disproven

`premise.disproven()` = REFUTED ∪ false-stamped, and `render_disproven()` puts it at the
TOP of a replacement's brief with the reason each one failed, including SH's
`stamp_reason` and the rival in `holds_reason`.

This closes the gap recorded in §"What this version does NOT do" of the first draft. The
old block was `render_refuted()`, which is empty unless a validator produced a REFUTED —
and a false stamp deliberately leaves the status VERIFIED. So on the commonest trigger
the alternative agent received **nothing the runner enforced**; its whole brief was SH's
own prose. That is how v1.4.3's Q216 replacement was handed the incumbent's reading and
came back with the incumbent's answer.

`deviation_violations` now keys on `disproven()` too, so the one field that makes a SPAWN
an *alternative* is required on the trigger that needs it most.

`render_for_senior` deliberately still uses `render_refuted()`: a false stamp is SH's
reading, not a settled refutation, and telling every active senior "this is dead" before
a validator has ruled would overreach.

### 8. Per-worker cost attribution

`UsageTracker` keyed `(qid, role)`, so every senior on a question landed in one `senior`
bucket. Q329 spent $1.58 across four workers and no artifact could say whether that was
four workers at $0.40 or one runaway.

`sid:<worker>` is now a LangChain tag set by `SplunkWorkerPool._run` / `.clarify`
(threaded from `SeniorSession.sid` and the validator's `vid`), the tracker keeps a
parallel `(qid, worker)` bucket, and `metrics.json` gains `cost_by_worker` with per-worker
tokens, dollars and **`cache_hit_pct`** — the number the provider-caching question is
actually asked of.

### 9. Reading an image that only exists as base64

New `agent/v1/vision.py` plus a `read_image_in_field` tool on the senior's toolset
(renamed `read_image` and rebuilt in §14).

**The design constraint is context, not capability.** Q217's `image001.jpg` is ~226 KB of
base64 in `attach_content`. A tool taking the bytes as an argument would make the senior
carry all of it through its own context to make the call, and again in the transcript
afterwards. So the tool takes an **SPL locator** (`spl`, `field`, `question`), runs the
search itself, decodes server-side, and returns only the vision model's short answer.
**The base64 never enters any agent's context.**

Division of labour: the vision model is asked a *perceptual* question and the senior does
the reasoning. A vision model asked to answer a CTF question would guess, and a guess in a
tool result is indistinguishable from evidence.

**Probed against NIM, 2026-09-22:**

| model | result |
|---|---|
| `meta/llama-3.2-90b-vision-instruct` | **504 Gateway Timeout** — did not answer |
| `nvidia/nemotron-3-nano-omni-30b-a3b-reasoning` | **works** |

Accuracy on the two shapes that matter, using synthetic images (not dataset artifacts):

- a vertical bar chart → *"bar chart"*. Correct perceptually; Q217's scoreboard answer is
  "Column Chart", which is Splunk's menu name for it. That mapping is the senior's job,
  and the tool's docstring now says so explicitly.
- one word rendered far larger than the surrounding text → **`Splunk`**, which is Q329's
  exact official answer.

Both models are priced at 0 in `PRICES_PER_1M`, per the standing NIM decision, so run
totals continue to understate true spend by whatever NIM would bill. `llama-3.2-90b` is
kept first in `VISION_MODELS` as the operator's stated priority, with fallback — NIM lists
far more models than it serves and a dead id returns a bare 404, so one id is not enough.

### 10. The scenario briefing, and prompt hygiene

The operator supplied the pre-event scenario. Its overlap with the existing prompts was
removed (the "elite responder" persona, "complete access to Splunk", "craft SPL"), and the
rest is a SITUATION paragraph placed **first** in `SH_SYSTEM_PROMPT` and **first** in
`SENIOR_BRIEF` (once per spawn, never per round). "APT" was removed from both prompts and
from `splunk_agent.SYSTEM_PROMPT`; "August 2018" stays. `orchestrator.py` was deliberately
left alone: the compiler loop is pinned for A/B.

The C3 validity-vs-soundness example no longer names a question or an IP. It is now the
generic shape: a senior quotes genuine rows showing that X alone has property P, and is
still wrong because another entity fits the question's actual wording better. The same
Q216 example was scrubbed from the `PremiseStamp` docstring, which pydantic ships to SH
inside the JSON schema, so it was prompt text too.

### 11. Every rejection names the SOP step it breaks

`conversation.with_step` / `at_step` render each gate line as
`[C3] <live reason> → re-read C3.` The step text is not repeated, since SH has it in its
system prompt. `grade_violations` and `directive_violations` tag their own lines. The rest
are tagged at the call site in `sh_loop`: C5 open questions, B5 overlap, E3 deviation,
F2–F3 audit, C3 stamp, C4 nomination, C6 ceiling, F2 ledger, G2–G3 unanswerable, and C7
for runner-refused updates. `tests/test_rejection_steps.py` fails if any gate emits an
untagged line.

### 12. An unreachable operator: skip once, pause on the second

`QuestionState.transport_failures`. The first `api_failed` on a question with no operator
reachable still SKIPs (v1.4.3). A second on the same question re-raises `RunPaused`:
twice is an outage the loop cannot plan around, and resume (13) means a pause no longer
throws away the question.

### 13. Wave-level resume

New `agent/v1/resume.py`. `run_question` snapshots at the top of every turn, after the
previous turn and its wave are fully applied, to `<run>/resume_state/<QID>/snapshot.pkl`
(atomic replace). The snapshot holds SH's messages since the opening, QuestionState, the
premise ledger, every SeniorSession's fields, kinds/subqs/unread/reports/grades, the
validators spent, the CLARIFY texts, and each live senior's LangGraph thread state.
Threads are exported via `SeniorPool.export_thread` and written back onto the same
thread_id with `import_thread` (`update_state(..., as_node="agent")`).

Resume is automatic. `--run-name X` on a question that has a snapshot prints
`↩ resuming Qxxx from turn N` and continues. Only the in-flight turn and its wave are
re-run. System messages are rebuilt from the **current** code; the snapshot holds the
conversation, not the prompt. The runner deletes the snapshot once the question is
recorded in `run_summary.json`. To force a fresh start, delete the folder.

SH's cross-question memory (`sh_history`) is now saved to `<run>/sh_history.pkl` after
each question and reloaded at start. Before this, a resumed process gave SH an empty
memory.

**Deviation from the agreed design.** Senior threads are stored inside our own per-turn
snapshot, not in a SQLite checkpointer. SQLite persists every graph step, including half
a round, which would have to be rolled back to the turn boundary on resume. The snapshot
is consistent by construction. For the same reason there is no separate mid-turn
"flush on error": the last boundary is already on disk when anything fails.

Verified by `test_a_paused_question_resumes_from_its_last_turn`: pause on the second
outage, re-run the same question, and SH resumes with its turn-1 history at turn 2. Also
checked by hand on a real LangGraph graph with the senior graph's node shape: an exported
thread imported into a fresh MemorySaver, then invoked, sees round 1's messages.
Known ceiling: cost spent inside the killed segment of an unfinished question is not
carried over, because `token_usage` is only written when a question is recorded.

### 14. The image tool guarantees pixels, and finds the image by format

The §9 tool read one named field, which does not work where it mattered: on stream:smtp
the attach_* fields are unreliable at search time, and the image exists only inside
`_raw` as an RFC822 message split across a JSON list. It is now
`read_image(spl, question, name="", extract_spl="")`.

- **The runner finds the image, by format, not by field.** `vision.extract_images` reads
  the event's whole `_raw`. It walks JSON, rejoining a list of strings so a chunked
  message parses as MIME, and parses MIME parts with the `email` library. It also decodes
  data: URIs, base64 runs (≥200 chars) and hex runs, and scans raw bytes for image
  signatures (an HTTP body carried as text). Everything is deduplicated by pixel hash and
  labelled by MIME filename where there is one.
- **Pixels only.** Every candidate is magic-checked, decoded by Pillow and re-encoded to
  PNG, so EXIF, comments, XMP and trailing bytes never reach the vision model. A test
  hides text in a JPEG COM segment and asserts it is gone.
- **Never guesses.** With several images and no `name`, it lists them (label and size)
  instead of picking one. With none, it lists what the event does hold (JSON, MIME parts
  and their types) and points to `extract_spl`.
- **Fallback (`extract_spl`).** Used only when the runner finds nothing. It is a search the
  senior writes to isolate the encoded image. The runner runs it and applies the same
  extraction and re-encode. Its output never returns to the senior.
- Logs only: no URL is ever fetched.
- `pillow>=10.0` added to `agent/requirements.txt` (12.2.0 was already installed).

**Verified against the real Q217 events (not committed; scratch only).** One Splunk search
confirmed `_raw` comes back untruncated: `len(_raw)` in SPL = 255,665 = characters
received, and the JSON parses. On all three `image001.jpg` emails the extractor finds
exactly one image, labelled `image001.jpg` (3072x870, 300x499, 252x56), in 0.03–0.43 s.
The MIME payload's MD5 matches the dataset's own `attach_content_decoded_md5_hash` on all
three. The vision model was not called in this check.

### 15. The image tool read only the first matching event

Found live in `v1.4.4_smoke5_r1`, on Q217. The senior's search named the right SMTP session
by `flow_id`, but Stream records one session as 5 events (greeting, commands, message).
`read_image` ran with `max_results=1` and read a 502-byte QUIT record, so it said "No
image found". The 481 KB message event held image002.jpg and image003.jpg, and the
extractor finds both when given that event. The senior spent several `extract_spl`
attempts before diagnosing this itself.

Now the tool reads up to `MAX_EVENTS` (10) matching events and extracts from all of them.
Without `name`, it sends every image found to the vision model one by one (up to
`MAX_IMAGES`, 5) and returns one labelled answer per image, leaving the choice to the
senior. With `name`, it describes only that image. When nothing is found, it says
"read N of M matching events". The docstring tells the senior to narrow the search to
one event when it is sure, and that matching a few is fine when it is not. This replaces
§14's "list and ask for `name`". Test:
`test_the_tool_reads_every_matching_event_not_just_the_first`.

### 16. The field manifest advertised stream:smtp fields that do not exist

`agent/botsv3_fields.json` listed 17 fields for stream:smtp, and 3 of them are not in the
data: `attach_content{}`, `to` and `from`. `fieldsummary` over all 879 events finds
`attach_content{}` in 0. The attachment bytes exist only inside `content`, as the whole
MIME message. The list had been hand-seeded in `335e104`, not scanned, and
`build_manifest.py` skips any sourcetype that already has fields, so it was never
corrected. The Q217 senior kept building `extract_spl` around `attach_content` because its
field lookup said the field existed.

Rebuilt from the data: the entry was emptied and `build_manifest.py` re-scanned it. It now
has 94 real fields, including the 8 real `attach_*` metadata fields; the phantom 3 are
gone. Runtime `_manifest_expand` is not the cause, because it adds only fields returned
from real events. A read-only audit of the other 101 sourcetypes is running.

### 17. A resumed question starts with a fresh outage count

Found live on Q328. The snapshot carried `transport_failures=1`, so after a relaunch the
first HTTP 500 from the senior provider counted as the second and paused at once. Every
relaunch therefore bought exactly one provider error. The resume branch now resets the
count to 0: the relaunch is the operator decision the pause was waiting for. Test:
`test_a_resumed_question_gets_a_fresh_outage_count`.

### 18. Vision models: Nemotron first, gpt-5.4-mini as the fallback; Llama dropped

Operator decision, 2026-09-23. `meta/llama-3.2-90b-vision-instruct` returned 504 on every
call this session. Worse, as the first model tried it cost a full timeout on every image
before the fallback ran. On Q329 of the live smoke run, Nemotron then returned 503
"ResourceExhausted: Worker local total request limit reached (16/16)", so the call failed
outright. `VISION_MODELS` is now `(nemotron-3-nano-omni, gpt-5.4-mini)`.

- `_client(model)` routes `nvidia/`/`meta/` ids to NIM (`NIM_API_KEY`) and everything else
  to OpenAI (`OPENAI_API_KEY`).
- gpt-5 models reject `max_tokens` and spend part of their budget on reasoning, so OpenAI
  calls send `max_completion_tokens=max(max_tokens, 2000)`.
- The fallback is priced at 0 under its own key, `gpt-5.4-mini (vision)`, so the paid
  `gpt-5.4-mini` row used by other callers is untouched.
- Live probe on a synthetic 4-bar chart: gpt-5.4-mini answered "rectangular bars… each
  bar is vertical".

Not done: the tool still does not pass the usage tracker to `describe`, so vision calls
are not counted in run totals. That does not matter while every vision model is priced
at 0.

### 19. Every stamp re-reads the question and checks a set in both directions

From the Q216 root-cause analysis (`v1.4.4_smoke5_r1`). The load-bearing premise claimed a
set: "the complete Monero-classified set is these six flows". SH stamped it sound after
weighing only one rival, "more rows exist elsewhere", which checks for MISSING members.
Nobody asked whether every member of the set does what the question's verb requires. One
flow did not, and the value moved by one second. The directive had also paraphrased the
set as "the six Monero-generating flows" before any measurement, so the paraphrase, not
the question, was what got checked.

Operator direction: make every grading of a premise go back to the question's own words.
The change is in three places SH reads at every stamp, with no question-specific content:

- **C3 (system prompt):** re-read the question word by word, verb and every qualifier,
  and judge the claim against those words rather than the working summary. A claim about a
  set has a rival in both directions: a member that is missing, and a member that is
  present but does not do what the question requires.
- **Per-wave STAMP FIRST line:** the same two reminders, in one sentence, every wave that
  owes stamps.
