# v1.4.5 — SH memory that lasts 53 questions

> **Status: BUILT, not yet smoke-run.** Plan written 2026-09-23 from the design agreed with
> the operator; implemented the same day (see the changelog at the end).

## Why this version exists

SH is meant to run the whole question set in one conversation, about 53 questions, and to
carry what it learned from one question into the next. Today it cannot.

**Measured on `v1.4.4_glm-5.3_smoke5_r1`** (tokens counted with tiktoken o200k, the GPT-5
encoding):

| piece | tokens |
|---|---|
| `SH_SYSTEM_PROMPT` + dataset briefing (fixed) | 4.9K + 2.9K ≈ 7.8K |
| One question's SH conversation | Q216 5.8K · **Q217 25.1K** · Q224 9.8K · Q328 11.8K (mean ≈ 13K) |
| Cross-question memory actually sent (`MAX_HISTORY_MSGS = 24`) | ≈ 16K |

1. **Today's failure is forgetting, not overflow.** `sh_loop.py:623`
   (`msgs += _window(history or [])`) sends only the last 24 messages. After four
   questions that window already starts partway through Q224: Q216 and Q217 are gone, and
   the cut lands mid-question. Across 53 questions SH would remember roughly the last one
   and a half.
2. **Removing the window alone would overflow.** At about 13K per question, raw history
   reaches 60% of gpt-5.4's 272K input window (163.2K) around **question 12**, and 272K
   around **question 20**.

v1.4.5 replaces the blind 24-message window with a deliberate memory: every finished
question is summarized once, the summaries stand in for old transcripts when space runs
short, and SH can pull any past question back in full when it needs to.

## Decisions (operator, 2026-09-23)

| # | decision |
|---|---|
| D1 | Swap threshold = **60% of 272K = 163,200 tokens** of SH prompt (gpt-5.4 input window). |
| D2 | Every past question keeps: the **full question text**, the **answer**, and a **reasoned flow** (each step says what was found and why it led to the next), plus a prose step-by-step derivation. |
| D3 | "Keep what's correct only" = **option (a)**: drop dead ends and disproven premises, keep one "ruled out" line per question. The scoreboard's correct/wrong verdict is **never** used or shown. |
| D4 | SH may **RECALL** any past question's conversation, reports, ledger or summary. A RECALL **costs no SH turn** (capped at 2 per question). |
| D5 | Summarizing is **verbose**: every step is printed and logged. |
| D6 | Summarizer = a separate, cheap model: **gpt-5.4-mini** (already in `PRICES_PER_1M`, paid row, costed under role `memory`). |
| D7 | The memory index is not just a list of titles. Each entry carries the question, the answer and enough of the reasoning that SH understands it on its own and knows whether to read on. |
| D8 | Summaries are written **once**, when a question finishes. The swap at the threshold is a pure replacement, with no model call; a summary is never summarized again. |

## Borrowed patterns

| from | pattern | how v1.4.5 uses it | what it does not take |
|---|---|---|---|
| LangChain v1 `SummarizationMiddleware` | token-based `trigger` (can be a fraction of the context), `keep` recent messages, a separate cheaper `model`, a custom `summary_prompt`, old messages **replaced** by a summary | the 60% trigger, the gpt-5.4-mini summarizer, a fixed summary template, raw transcripts replaced by their summaries | it attaches to `create_agent` tool agents (SH is a structured-output loop); it cuts by messages or tokens and can split a question; `trim_tokens_to_summarize` defaults to 4,000 tokens, which would drop most of a 25K question; it builds one rolling blob |
| Letta (formerly MemGPT) | **memory blocks**: labelled, size-capped sections always in context; **compaction** of old messages with the full history kept; **`conversation_search`**, where the agent pulls back exact old messages | the memory-index cards and knowledge blocks are always-present blocks; nothing is deleted from disk; RECALL is SH's `conversation_search` | Letta is a whole agent server with its own runtime; adopting it would mean rebuilding SH and losing the gates, ledger, stamps and waves |

Both library descriptions were checked against their current docs (context7) on 2026-09-23.

## Design

### 1. What SH's context holds at question N

```
┌ 1  SH_SYSTEM_PROMPT (current code) + dataset briefing             ≈ 8K   as today
├ 2  CASE FILE digest                                              small  as today
├ 3  MEMORY INDEX: one card per past question                      ≈ 250 × N   always
├ 4  KNOWLEDGE BLOCKS: entities · feed & field facts · working SPL ≤ 6K   always
├ 5  DETAILED SUMMARIES of older questions                         ≈ 1K each
├ 6  RAW TRANSCRIPTS of recent questions, while they fit           varies
└ 7  The current question (never summarized)                       varies
```

Sections 3 and 4 are always present. Sections 5 and 6 trade places as space runs short
(§4). Worst case after 53 questions, with every past question at section 5:
8K + 13K (cards) + 53K (summaries) + 6K (knowledge) ≈ **80K**, half the threshold. A second
level of compression is therefore not built (YAGNI); §8 names the fallback if it were ever
needed.

### 2. The per-question memory (written once, when the question ends)

One `gpt-5.4-mini` structured-output call per question, returning `QuestionMemory`:

| field | content | in context as |
|---|---|---|
| `qid`, `question`, `guidance` | the question text **verbatim** plus its answer guidance | card |
| `answer` | what SH submitted (or `NO_ANSWER` / `NOT_ANSWERABLE`) | card |
| `flow` | 4–6 steps; each says what was found **and why that led to the next step** | card |
| `derivation` | prose, first search to final answer: which feeds, which pivots, why each choice | summary |
| `verified_premises` | one line each: id, claim, and the stamp's soundness reason (VERIFIED only) | summary |
| `validator_verdicts` | one line each: premise, verdict, the rival it tested | summary |
| `entities` | e.g. `BSTOLL-L = 192.168.247.131 = Bud Stoll's laptop` | merged into knowledge |
| `feed_facts` | e.g. `stream:smtp: one session = several events; attachment bytes only in content` | merged into knowledge |
| `working_spl` | one canonical search per finding, with what it returns | merged into knowledge |
| `ruled_out` | ONE line: the disproven paths, so they are not walked again | summary |

**Card example** (Q216, as it should have been):

> **Q216** — "According to the Cisco NVM flow logs, for how many seconds does the endpoint
> generate Monero cryptocurrency?" (round to the nearest second)
> **Answer: 1666**
> 1. The question names Cisco NVM, which here is `source=cisconvmflowdata` under sourcetype
>    syslog, so only that feed counts.
> 2. No process or port there is a miner; the Monero traffic is chrome.exe on BSTOLL-L
>    (192.168.247.131, Bud's laptop) talking to Coinhive, a browser Monero miner.
> 3. Coinhive shows two kinds of flow: `coinhive.com` loads the script, and `ws0xx.coinhive.com`
>    are the mining servers. Generating Monero means the mining servers, so only those count.
> 4. The flows overlap, so the duration is wall-clock time from the first mining-server start
>    (fss) to the last end (fes), not the sum.
> 5. 1534773920 − 1534772254 = 1666 s.

**Input to the summarizer** is only what SH itself saw: this question's SH transcript,
its premise ledger (`premise_ledgers/<QID>.json`) and the submitted answer. **Never** the
answer key, the scoreboard verdict or `botsv3_answers.json`. A test enforces this (§7).

Written to `<run>/memory/<QID>.json` (the structured record) and `<QID>.md` (readable),
atomically, before `resume.clear` runs. A question that dies before this point has no
memory yet, and the resume path (v1.4.4 §13) re-runs its tail as it does today.

### 3. Knowledge blocks

Three size-capped lists, rebuilt after every question by merging the new `QuestionMemory`:

- **Entities**, keyed on the identifier (host, IP, account). A later question's entry for
  the same key replaces the earlier one.
- **Feed and field facts**, keyed on sourcetype.
- **Working SPL**, keyed on sourcetype plus purpose. The newest wins; capped at N per sourcetype.

The merge is deterministic (dict keyed as above), with no second model call. Cap: 6K
tokens in total. When over the cap, the entries touched least recently drop first; they
stay in each question's `memory/<QID>.json`, reachable through RECALL.

The incident **timeline** is not duplicated here: the case file already carries it
(`render_digest()`).

### 4. The swap (at the start of each question)

1. Build SH's prompt as sections 1–7 with every past question at its best available form:
   raw transcript if held, else its summary.
2. Count tokens with tiktoken o200k. The count is exact; LangChain's default estimates by
   characters.
3. While the count is above **163,200**: replace the **oldest** past question still held raw
   with its summary (card + detailed summary). Whole questions only; never the current one.
4. Log every swap (§6).

No model call happens here. Every summary already exists from §2.

This replaces `MAX_HISTORY_MSGS` / `_window` in `sh_loop.py`. `history` changes from a flat
message list to `{qid: [messages]}` in question order, so a swap removes exactly one
question's messages. `resume.save_history` / `load_history` keep the same file and change
format; an old flat-list `sh_history.pkl` is loaded as a single unnamed segment.

### 5. RECALL — SH asks for a past question in full

A new route next to CLARIFY and COMMAND, in `conversation.py` (`ROUTES`, the `route`
Literal and its validator):

```
route = "RECALL"
recall_qid   = "Q217"
recall_what  = "summary" | "conversation" | "ledger" | "report:<sid>:<round>"
```

The runner reads the file (`memory/<QID>.md`, `<QID>/conversation.md`,
`premise_ledgers/<QID>.json`, `<QID>/reports/<sid>_round_<n>.md`), truncates it to 8K tokens
(saying so), and returns it in the next message as `RECALLED <QID> <what>`.

**No turn cost.** A turn made up **only** of RECALL entries refunds its `record_turn()`
(`sh_loop.py:689`). A turn that mixes RECALL with other routes counts normally. **At most 2
RECALL turns per question**; a third is rejected with a tagged line (`[B7]`, new SOP step).
A RECALL naming an unknown question or file returns what exists for that question instead.

The SOP gains one step (B7): *"Before planning, read the memory index. If a past question
shares this question's entities, feed or artifact, RECALL its summary; RECALL its
conversation or a report only when the summary leaves out what you need."* That is how SH
starts every question from its memory rather than from zero.

### 6. Verbose logging

Every step is printed to the console **and** appended to `<run>/memory/compaction_log.md`:

```
[SH MEMORY] Q231 finished → summarizing with gpt-5.4-mini (21,340 tok in)
[SH MEMORY] Q231 summary: 912 tok (card 264) → memory/Q231.md
[SH MEMORY]   card:  Q231 — "…question…" · Answer: … · 1. … 2. … 3. …
[SH MEMORY]   knowledge: +3 entities, +1 feed fact, +2 SPL (5,480 / 6,000 tok)
[SH MEMORY] prompt for Q240: 171,204 tok > 163,200 → Q216 raw 5,846 → summary 1,004 … Q224 → now 128,450
[SH MEMORY] RECALL Q217 ledger → 2,105 tok (recall 1 of 2, no turn charged)
```

The full text of each new summary is written to the log when it is created, so the
operator can read exactly what SH will remember.

### 7. Files and tests

| file | change |
|---|---|

| `agent/v1/sh_loop.py` | `run_question` builds its prefix with `render_memory()` instead of `_window(history)`; RECALL route handling and turn refund; SOP step B7 in `SH_SYSTEM_PROMPT`; drop `MAX_HISTORY_MSGS` / `_window` |
| `agent/v1/conversation.py` | `RECALL` in `ROUTES` / `route`; `recall_qid`, `recall_what` fields and validator; a gate for the 2-per-question cap |
| `agent/v1/run_all_v1.py` | after a question is recorded: `summarize_question()` then `merge_knowledge()`, before `resume.clear` (`run_all_v1.py:720`); history kept per question |
| `agent/v1/resume.py` | history stored per question; old flat format still loads |
| `agent/v1/usage_tracker.py` | nothing new: the summarizer uses the paid `gpt-5.4-mini` row under role `memory`, so it appears in the cost-by-role breakdown |

Tests (`agent/v1/tests/test_sh_memory.py`):

1. The swap replaces whole questions, oldest first, never the current one, and stops as
   soon as the prompt is under the threshold.
2. No swap below the threshold: raw transcripts stay.
3. The summarizer's input never contains the answer key or a scoreboard verdict (a sentinel
   planted in `botsv3_answers.json` must not appear in the captured prompt).
4. A card renders the verbatim question, the answer and the flow; a card without a flow is
   rejected by the model schema.
5. Knowledge merge: same key replaces, the cap drops the least recently touched entries,
   and dropped entries stay in `memory/<QID>.json`.
6. RECALL: returns the named file, truncated at 8K with a note; an all-RECALL turn is not
   counted; the third RECALL turn is rejected with `[B7]`.
7. Resume: per-question history round-trips through `save_history` / `load_history`; an old
   flat `sh_history.pkl` still loads.

### 8. Verification

- **Unit tests** as above, then the full suite.
- **Smoke (≤5 questions, per the cost policy).** Five questions never reach 163.2K, so the
  runner takes `--memory-threshold <tokens>` (default 163,200) and the smoke run sets it
  low, e.g. 20,000, so the swap fires by question 2 or 3. Check: summaries are written, the
  log shows the swap, SH's later prompts carry cards instead of raw transcripts, and RECALL
  works if SH uses it.
- **Cost check.** The summarizer's cost per question from `metrics.json` (`cost_by_role.memory`);
  expected ≈ $0.02.

**If summaries ever outgrow the threshold** (not expected, ≈ 80K worst case): drop the
oldest *detailed* summaries from context and keep their cards; the detail stays reachable
through RECALL. Not built until a measurement shows it is needed.

## Out of scope

- Summarizing within a question (section 7 is always raw). Q217, the largest, was 25K.
- Senior memory. Seniors are question-scoped and already compact their own threads.
- Using the scoreboard verdict in any form (D3).
