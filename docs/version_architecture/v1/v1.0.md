# SIEM Agent v1.0 — Hierarchical Multi-Agent Architecture

> **Code**: `agent/v1/`
> **Predecessor**: [v0](../v0/v0.md) — single LangGraph ReAct agent, 21/58 (36.2%), $7.73.

## What changed vs v0

v0 was one agent doing everything. v1 splits the work into a **mastermind orchestrator (SH)**
that plans and delegates, and **disposable Splunk workers** that do the actual querying. A
separate **Extractor** strips and validates the final answer before a single scoreboard
submission. The goal is to lift the score on genuinely multi-hop questions while making every
step independently inspectable.

## Components

| Agent | Model | Memory | Role |
|-------|-------|--------|------|
| **SH (orchestrator)** | gpt-5.4 | **persistent across the whole run** | Plans, decomposes (optionally), delegates, assembles the final answer. Never touches Splunk. |
| **Senior Splunk** | gpt-5.4 | fresh per task | The v0 graph reused verbatim (verify→execute gate, 6 tools, Intention protocol) + ESCALATE protocol. Multi-step reasoning. |
| **Extractor** | meta/llama-3.3-70b-instruct (NIM) | none | Prose-strip to the bare answer + format/plausibility validation. Submits once. |

> Junior Splunk (Llama-3.3, simple single-hop lookups) + senior/junior routing is **deferred
> to v1.1**. v1.0 routes all data lookups to the Senior.

## Control flow (per question)

```
SH (persistent thread)
  ├─ optionally decompose into atomic sub-questions
  ├─ spawn_senior(subquestion)  ─► fresh Senior worker (v0 graph, new thread_id)
  │                                 └─ returns {answer, status, spl_used, sourcetypes}
  ├─ status != solved  ─► failed_delegations++  ─► re-scope smaller, delegate again
  ├─ ... (sequential, one worker at a time) ...
  └─ plain-text FINAL ANSWER   (no tool call ⇒ ReAct loop ends)
        │
        ▼
  Extractor: strip + validate against answer_guidance
        ├─ invalid ─► feedback to SH (capped retry), no submission
        └─ valid   ─► scoreboard.submit()  (exactly once)
```

Termination is the standard ReAct pattern (no `finalize` tool): when the SH returns a
message with no tool call, the graph routes to `END`. Hard caps: `SH_MAX_ROUNDS = 12`
delegation turns/question; `EXTRACTOR_MAX_RETRIES = 1`.

## Key design decisions

- **Decomposition is optional** — most BOTSv3 questions are atomic; forcing decomposition on
  them only adds cost and a failure mode. The SH may delegate a whole question in one call.
- **Single submission per question** — the Extractor validates *format only* (it has no ground
  truth). Feedback to the SH happens *before* submission. No resubmit-on-wrong loop, which
  would brute-force the local scoreboard and invalidate the score as a capability measure.
- **SH keeps cross-question memory; workers are stateless** — the mastermind is the only
  stateful entity (one persistent MemorySaver thread for all 58 questions), so it reuses
  entities/findings across questions. Workers get a fresh session every task for isolation
  and reproducibility. Restating context inside each `subquestion` is mandatory because
  workers cannot see the SH's memory.
- **Structured findings, not just prose** — workers return the SPL they ran and the
  sourcetypes they touched, partly mitigating the context-fragmentation risk of handing
  prose summaries between agents.
- **NIM vs OpenAI token param** — `create_agent` sends `max_completion_tokens` for OpenAI and
  `max_tokens` when a `base_url` (NIM) is set, so the same v0 graph drives both backends.

## Tracking & observability (req c, d, e, f)

- `failed_delegations` — cumulative count of delegations where the worker returned
  `too_big`/`failed` (i.e. the SH scoped the task poorly). Primary v1 tuning metric, in the
  run JSON.
- `extractor_rejections` — times the Extractor bounced the SH's answer for re-work.
- Each worker's **full state** (serialized message trace, SPL, sourcetypes) is stored under
  `delegations[]` in `run_summary.json`.
- Hierarchical logs (see below) with a `=== TASK ===` header at the top of every worker log.

## Logging layout

```
log/v1/run_1.<minor>/        (auto-incrementing; full runs only)
  SH/             sh_<qid>.log
  Senior Splunk/  senior_splunk_<n>_<qid>.log     (=== TASK === header)
  Junior Splunk/  (from v1.1)
  Extractor/      extractor_<qid>.log
  timeline.md     sequential narrative: SH plan → worker 1 → ... → replan → FINAL
  run_summary.json
```

Test runs (`run_all_v1.py --ids` / `--limit`) go to `log/temp/<ts>/` and are never logged as
a versioned run.

## Results

**Full run: 2026-06-29 — `log/v1/run_1.0/`**

| Metric | v1.0 | v0 |
|--------|------|----|
| Correct | 20/58 (34.5%) | 21/58 (36.2%) |
| Points | 5650/23050 | 5750/23050 |
| Cost | $7.36 | $7.73 |
| Failed delegations | 6 | n/a |
| Extractor rejections | 0 | n/a |

v1.0 showed marginal regression vs v0 (-1 question, -100 pts). The SH+Senior pairing successfully handled multi-hop pivots (Q209, Q219, Q305, Q317, Q330) but revealed three new failure modes:

1. **Extractor over-censorship** — Llama-3.3-70B refused to output answers that looked like credentials (Q220 AWS key, Q303/Q320 password), costing 3 questions.
2. **SH credential refusal** — Q320 was skipped with delegations=0: the SH recognized the question as "same password as Q303" from memory and short-circuited without even delegating, then the SH itself refused to produce a credential answer.
3. **Extractor format bleed** — Q331 computed the correct IQR value (1368) but the Extractor returned "UF = 1368" instead of the bare number, causing a wrong submission.

See [scoreboard_result/v1/v1.0.md](../../scoreboard_result/v1/v1.0.md) for the full question-by-question breakdown.
