## Changelog

- Discovery widened to the `source` axis. Every tool was keyed on `sourcetype`
  alone, so the 78,459 Cisco NVM flow events that sit under `sourcetype=syslog`
  and are addressable only as `source="cisconvmflowdata"` were unreachable —
  Q216's log shows 434 `sourcetype=` against 2 `source=` across 168 discovery
  calls. Added `_scope(sourcetype, source)` in `splunk_client.py` and a new
  `get_sources(sourcetype, keyword, top_n)` tool returning
  `stats count by source, sourcetype`; `get_sourcetype_fields`, `get_field_values`,
  `sample_events` and `get_raw_events` all now take `source`, and `sourcetype`
  became optional on each. `run_splunk_search`'s docstring said "Always include a
  sourcetype filter" and `SYSTEM_PROMPT` said "Never run a search without a
  sourcetype filter" — both forbade the one query that answers Q216, so both were
  rewritten to two-axis wording, and the prompt's worked example now shows the
  pivot. Verified by `tests/test_source_axis.py` (6 tests; 189 pass).

- Per-worker latency broken out. `_run_senior` is the one choke point every
  worker reaches Splunk through (executor, verifier and adjudicator all call
  it), so a single `time.perf_counter()` there stamps `duration_s` onto each
  result; `_delegation_record` carries it, and `build_metrics_row` emits
  `latency_s.workers` (per `senior#N`) plus `latency_s.worker_total`. Before
  this, `latency_s` had one opaque `sh` number - run 3's Q216 showed 1332s in
  SH with no way to see where it went. `worker_total` exceeding `sh` is the
  only readout of whether the fan-out actually overlapped. Verified by
  `test_worker_latency_is_broken_out_per_worker_and_summed` (183 tests pass).

- Per-call output cap raised 4096 -> 16384 for every LLM call, and a new
  per-worker runaway guard added. 4096 was chosen in the first commit (2026-06-17)
  for Llama 3.3, a model with no hidden reasoning; GLM-5.3 spends that budget on
  chain-of-thought before writing `content`, so a truncated worker returns an empty
  answer that reads as a failed delegation. Two calls in the Q216 run stopped at
  exactly 4096 output tokens. 16384 is well clear of any observed answer and is
  portable - GLM-5.3's own hard ceiling is 32768 (probed: 65536 and 100000 are
  rejected with HTTP 400), so pinning to the maximum would tie the config to one
  provider. Runaway generation is now bounded per worker instead: `OUTPUT_TOKEN_CAP
  = 100_000` in `splunk_agent.py`, accumulated from each response's
  `usage_metadata` into `AgentState.output_tokens`. Measured typical worker output
  is ~11-12K tokens across all its calls (137,165/12 and 110,238/9 over the two
  Q216 runs), so the cap is ~8x typical - reaching it means stuck, not thorough.
- A worker crossing the guard now routes to the **HITL interrupt**, not to an
  ordinary failure. `splunk_subagent._run` sets `status="runaway"`, and
  `executor_graph` replaces its two hard-coded `== "api_failed"` checks with
  `INTERRUPT_STATUSES = {"api_failed", "runaway"}`, carrying the specific status
  through as the interrupt's `reason`. Rationale: SH replans around a reasoning
  failure, which would re-dispatch workers at whatever made the first one runaway;
  a human should decide instead. Test
  `test_runaway_worker_reaches_the_hitl_interrupt` asserts the pause and the reason.

- Extractor model swapped to `nvidia/nemotron-3-super-120b-a12b`. NIM decommissioned
  `meta/llama-3.3-70b-instruct` on 2026-08-26; every extractor call in the 2026-09-07
  Q216 re-run returned HTTP 410 "Gone", so the bare-answer step was skipped entirely
  and raw worker prose went to the scoreboard. Confirmed against NIM's live catalogue
  (81 models, no `llama-3.3` entry remains) and probed end to end: the new model
  returns `content='9'` for a prose-strip prompt with its chain of thought in a
  separate `reasoning_content` field, so `max_tokens=1024` stays necessary.
  Priced at 0 in `PRICES_PER_1M` by decision, so extractor cost reports $0.00 without
  the "not in PRICES_PER_1M" warning.
- Extractor no longer retries permanent statuses (`EXTRACT_FATAL_STATUS` =
  400/401/403/404/410/422). The 10+20+40+80s ladder exists for gateway blips; against
  a decommissioned model it burned 150s per question and failed anyway. Test
  `test_permanent_status_is_not_retried` asserts a 410 raises after one attempt.
- CLAUDE.md: added "New model or provider" - ask the user for the price of any new
  model/provider and add the row to `PRICES_PER_1M`; the extractor is priced at 0.
  Motivated by GLM-5.3 running a whole question costed at $0.00.

- Fixed the Q216 crash: the LangSmith parent `RunTree` moved out of the executor's
  `Send` payload and onto `ctx.parent_run_tree`. A `Send` payload is checkpointed
  graph state, and a live `RunTree` carries a client and locks, so the SQLite
  checkpointer raised `TypeError: Type is not msgpack serializable: Send` when the

  converted the crash into the empty-answer sentinel, so the run exited 0 having
  submitted an unchecked worker answer for 0/1000. `ctx` is process memory and is
  never checkpointed, so tracing still nests while nothing live reaches disk.
  Verified by reproduction: same crash on attempt 1, then resume on the same thread
  ran **zero** new paid workers and completed from the checkpoint. Regression test
  `test_a_live_object_in_a_send_payload_breaks_checkpointing` pins both directions.
- Added `zai-org/GLM-5.3` to `PRICES_PER_1M` at $1.40 input / $0.26 cached / $4.40
  output per 1M, derived from ten billed Featherless calls and reproducing every one

## Cost-attribution bug fix (2026-08-21)

`UsageTracker.on_llm_end` (`usage_tracker.py`) was billing every Senior worker's
LLM calls to the SH cost bucket instead of the Senior bucket. Root cause: a
Senior worker's `graph.invoke()` (`splunk_subagent.py` → `run_agent_traced`)
runs nested inside the SH run's still-active LangChain context, so the SH's
ambient `tags=["SH", qid]` (set at `orchestrator.py:933`) leak onto the Senior
call alongside its own explicit `["senior", qid]` tags. The old classification
checked `"SH" in tags` first, so a Senior call carrying both tags was
misclassified as `role="sh"` and double-counted into `_sh_cum`. Confirmed
against `log/v1/run_1.1/run_summary.json`: `__sh_cumulative__` showed 553,500
input tokens against SH's real (gpt-5.4) usage of only 21,832 — it had silently
absorbed nearly all of GLM's 531,668 Senior-worker input tokens.

This did **not** change the run-level total ($0.63 for run_1.1 is correct —
`__total__` sums by model, independent of role tags). It corrupted the
`sh`/`senior` **split**: every per-question `cost_by_role` breakdown
(`build_metrics_row`, `run_all_v1.py:143`) and `sh_question_tokens()` reported
SH cost that was actually SH+Senior combined, while the true Senior-only cost
was under-reported. Fix: the Senior worker's own explicit `"senior"` tag now
takes precedence over the inherited `"SH"` tag (`is_senior` checked before
`is_sh`). Regression test added:
`test_senior_call_with_leaked_sh_tag_bills_to_senior_not_sh`
(`tests/test_usage_attribution.py`), reproducing the real leaked-tag shape.
`python -m pytest agent/v1/tests/test_usage_attribution.py -q` → 4 passed.

## LLM failure resilience — SDK retry config + typed error reporting (2026-09-02)

Resumes the recovery-pipeline design handed over in
`docs/HANDOVER-2026-08-31-recovery-pipeline.md`. Scope this pass: make an LLM
failure survivable and legible, without building the pause/HITL machinery.

**Findings that shaped it** (read from installed `openai 2.42.0` /
`langchain_openai 1.3.2`, not from memory):

- `ChatOpenAI` passes `max_retries=None`, so the SDK's `DEFAULT_MAX_RETRIES = 2`
  was already active — SH and Senior calls were *already* retrying. The gap was
  never absent retry; it was the SDK's `DEFAULT_TIMEOUT = 600s`, which lets a
  stalled connection sit silent for 10 minutes per attempt (up to 30 across
  three). That is the reported "process died but is still running" symptom.
- The SDK retries 408/409/429/≥5xx and transport errors, honours `Retry-After`
  (when ≤60s), and applies jittered exponential backoff — but caps each wait at
  the module constant `MAX_RETRY_DELAY = 8.0s`. So the SDK **cannot** reproduce
  the Extractor's 10→20→40→80s ride-out of a multi-minute NIM outage. The
  Extractor's hand-rolled loop is therefore **not** redundant and was kept;
  hand-rolled backoff for SH/Senior would have been, and was not written.
- The `checkpointer` contradiction flagged in the handover (Q3) is **resolved as
  a documentation artifact**: that grep ran while the working tree was empty
  from the OneDrive incident. `run_all_v1.py:294` passes
  `<run_dir>/sh_checkpoints.sqlite` into `build_sh_agent_compiler`, which builds
  a **`SqliteSaver`** (`orchestrator.py:881-885`). SH cross-question memory is
  genuinely durable across process death. Senior workers use `MemorySaver` with
  a fresh `thread_id` per task, so worker state is intentionally not durable.
  `v1.1.md:301` ("a single `MemorySaver` thread") is stale and understates this.

**Changes:**

- **New `agent/v1/llm_errors.py`** — `describe_llm_error(exc, component,
  base_url)` and `provider_of(base_url)`. `str(exc)` on an openai exception
  prints only the response body, so a 429 and a 500 read identically in the
  logs; every failure line now names the exception type, HTTP status, the
  component (SH / Senior-N-Qxxx / Extractor) and the provider host. Used at all
  four failure sites. Description-only by design — retry stays the SDK's job.
- **Explicit timeout/retry budget on both `ChatOpenAI` constructions.**
  `splunk_agent.py`: `LLM_TIMEOUT_S = 120.0`, `LLM_MAX_RETRIES = 3` (Senior/v0
  workers take long tool-heavy turns). `orchestrator.py`: `SH_TIMEOUT_S = 90.0`,
  `SH_MAX_RETRIES = 3` (SH turns are plan/join text only). Named constants, not
  literals — these are calibration knobs for a slow endpoint.
- **`run_sh()` exception guard (`orchestrator.py`).** This was the only LLM call
  path in the pipeline with no `try/except` — an SH-side exception propagated
  out of the per-question loop and killed the whole run. Both callers are in
  `run_all_v1.py`, so the guard lives in `run_sh` once rather than at each call
  site. It logs via `describe_llm_error` plus a full traceback (so real bugs
  stay debuggable rather than being swallowed) and returns the `("", {})`
  sentinel.
- **SH-failure fallback (`run_all_v1.py`).** On the empty sentinel the runner
  skips the Extractor call entirely — there is no prose to strip — and takes
  `extractor_fallback_answer(...)`, the same path an Extractor outage already
  used. Emits a `sh_failed` event. The Extractor's own failure line and

## api_failed status + HITL pause + non-compliant-provider net (2026-09-04)

Closes the gap the aborted 2026-09-02 smoke exposed: an API failure was
indistinguishable from a worker that searched honestly and found nothing.

**Root cause.** `_classify()` (`splunk_subagent.py:99`) derives a worker's
`status` from the answer *text*, and a crashed worker's text starts with
`ESCALATE:` exactly like an honest give-up — so both collapsed onto `too_big`.
`status` drives every routing decision in the orchestrator (escalation at
`:537-540`, the joiner prompt at `:584`, the verifier at `:729`), and `too_big`
means *"this task was too large, decompose it"*. SH's programmed response to a
provider outage was therefore to split the task and dispatch **more** workers at
the same dead endpoint — the amplification mechanism behind v1.2's 62 failed
delegations and 50x cost blowup, observed live in the 2026-09-02 log (two
Featherless crashes → joiner `REPLAN` with 2 fresh tasks). The information to
tell them apart was already in the record (`iterations: 0`, `spl_used: []`);
`_classify` discarded it.

**Changes:**

- **`llm_errors.resilient_http_client()`** — an httpx transport that rewrites a
  `200` carrying an error envelope with no `choices` into a real `500`. This is
  the root-level fix for the Featherless case: a 200 is a *success* to the
  openai SDK, so `_should_retry` is never consulted and `max_retries` never
  fires. Rewriting the status at the transport boundary makes the provider look
  compliant to every layer above, so the SDK's own retry/backoff/jitter handles
  it and anything still failing surfaces as a typed `InternalServerError`
  instead of langchain's unclassifiable bare `ValueError`. Deliberately stricter
  than langchain's check (`base.py:1771`), which raises on *any* truthy `error`
  key: this requires `choices` to be absent, so a completion carrying a
  warning-shaped `error` survives. Wired into SH, all Senior worker graphs (one
  pooled thread-safe client) and the Extractor.
- **`status="api_failed"`** — set directly by `_run()` from the fact that it
  caught an exception, not by parsing text. Worker records also now carry
  `provider`. The existing `("too_big", "failed")` routing tuples exclude it, so
  an outage no longer increments `failed_delegations` or triggers decomposition.
- **New `agent/v1/hitl.py`** — the pause seam, written as *"persist state →
  emit a decision request"* rather than *"block on stdin"*. A blocking `input()`
  only works with a human at a terminal; under an agent harness stdin is the
  null device, so it would raise `EOFError` and turn a pause into a **new crash**
  in the environment the pipeline most often runs in. Two front-ends over one
  seam: a tty gets an interactive `skip`/`abort` prompt; otherwise the run
  writes `decision_request.json` and raises `RunPaused`. Partial state
  (`q_delegations`, `q_handoffs`) is flushed by plain JSON serialization — never
  an LLM summarization call, so preserving spent effort costs zero extra tokens.
- **HITL hook placed after the future-collection loop** (`orchestrator.py`).
  This resolves handover caveat (b) by construction: every future has already
  been `.result()`-ed at that point, so no Senior worker is in flight during a
  pause — nothing to cancel, nothing orphaned, no tokens wasted.
- **`EXIT_PAUSED = 75`** (`sysexits.h` EX_TEMPFAIL) in `run_all_v1.py`, so a
  pause is distinguishable from a crash (1) and success (0) by a supervisor or
  agent harness. The handler prints the resume command rather than a traceback.

**Verified:** new `tests/test_hitl.py` (6 tests) covers the transport rewrite,
the two no-false-positive cases (valid completion, completion + soft error),
non-JSON passthrough, `api_failed` tagging via a monkeypatched exploding
provider, and that a non-tty pause raises `RunPaused` and persists partial work
instead of calling `input()`. Full suite: **166 passed**.

**Still open:** `retry` as a HITL option is not wired (only `skip`/`abort`); the
circuit-breaker policy for a sustained outage (handover Q4) is unbuilt; and the
silent-death diagnosis (Q7) is still unconfirmed — the Splunk trial licence
expired 2026-08-15 and blocks any scoring run.

### Fix: `run_sh` swallowed the HITL pause (2026-09-04, same day)

The pause shipped inert. `RunPaused` subclasses `Exception`, so the `run_sh`
guard added earlier the same day caught it, printed it as an `[LLM ERROR]`, and
returned the `("", {})` sentinel — the runner then took the best-worker fallback
and carried on past the exact failure a human was being asked to decide about.
The pause never reached `main()`, so `EXIT_PAUSED` could never fire. Fixed with
an `except RunPaused: raise` ahead of the blanket handler. Regression test
`test_run_sh_lets_a_pause_through_instead_of_swallowing_it`. Suite: 167 passed.

Noted, not fixed: the verifier (`orchestrator.py:752`) and adjudicator (`:837`)
call `_run_senior` directly and swallow worker exceptions, so an `api_failed`
result there is ignored rather than escalated to a human. Only the executor path
raises for HITL today.

### HITL extended to the verifier and adjudicator (2026-09-04)

Closes the gap noted above. The pause logic is now one function,
`hitl.pause_if_api_failed()`, called at all three points where an `api_failed`
result is *observed*: the executor's post-collection loop, the verifier, and the
adjudicator (via the small ctx-aware `_pause_if_api_failed` adapter).

**Why the check can't simply live inside `_run_senior`**, which all three paths
share: that function's own docstring says *"called from ThreadPoolExecutor
thread."* In the executor path it runs on up to 6 threads at once, so pausing
there would have six threads racing for one `input()` prompt and clobbering one
`decision_request.json`, while their still-running siblings kept spending on the
same dead provider. The deciding property is the *thread*, not the function — so
the pause belongs at each single-threaded observation point, which is exactly
where the shared helper is called.

Both new call sites are placed **outside** their surrounding `try/except`, since
each has a blanket `except Exception` that would otherwise swallow `RunPaused` —
the same defect fixed in `run_sh` earlier today.

Tests: `test_pause_helper_ignores_healthy_results` (a `too_big`/`failed` result
is a reasoning outcome and must NOT pause) and `test_pause_helper_fires_on_api_failed`.
Suite: **169 passed**.

## Fan-out executor: one node per Senior worker (2026-09-04) — step 1 of 2

Adopts the architecture the user specified: each Senior worker becomes an
independent LangGraph node, with a conditional edge to a HITL node that
interrupts only after its siblings have finished. New module
`agent/v1/executor_graph.py`; **not yet wired into the SH graph** (step 2).

**Verified against the installed langgraph before building** (probe, no LLM
calls). With `Send`-based fan-out where one branch interrupts:

- all sibling branches still ran to completion (`workers executed: [0,1,2]`),
  and their results were present in state;
- the convergence node was correctly withheld (`join reached? False`);
- on resume **only the interrupted branch replayed** (`RE-executed: [1]`).

Two consequences shaped the design:

1. **"Interrupt only once the other dispatched agents finish" is free.**
   LangGraph runs every task in a superstep to completion before surfacing the
   interrupt, so no worker is cancelled or orphaned. No coordination needed.
2. **The interrupt must NOT live inside the worker.** `interrupt()` restarts its
   own node from the top, so a worker that interrupted would re-issue its own
   LLM call on every resume. Workers therefore *return* their result (checkpointed
   as real graph state) and a separate, side-effect-free `hitl` node interrupts.
   Resuming replays that node alone.

This also dissolves the objection recorded earlier against LangGraph-native
HITL. That objection was correct *for the old granularity*: interrupting inside
the 6-worker dispatcher node meant re-dispatching all six on resume. With one
node per worker the replay cost drops to a single cheap node, and `RETRY`
re-dispatches only the task that actually failed.

Topology: `dispatch --Send--> worker (xN) --> collect -->` {`hitl` | `dispatch`
(next wave) | END}, with `hitl -->` {`dispatch` (retry) | END (skip/abort)}.
The `$N` dependency DAG is preserved via `ready_tasks()`, which falls back to
one pending task rather than deadlocking on a malformed graph.

**Verified:** `tests/test_executor_graph.py` (8 tests) — parallel fan-out,
dependency ordering across waves, deadlock fallback, siblings completing despite
a pause, `RETRY` re-dispatching *only* the failed task, `ABORT`, sample
reduction, and the central one: **resume re-runs no worker at all**
(`calls == []`). Suite: **177 passed**.

**Step 2 (not done):** wire this in place of `executor_node`, porting the
sampling/handoff/delegation-record logic, and replace `RunPaused` with the
graph-native interrupt. Note the SH graph would need its checkpointer threaded
through and `run_sh` taught to resume with `Command(resume=...)`. Cannot be
integration-tested until the expired Splunk licence is restored.

## Step 2: fan-out executor wired into the SH graph (2026-09-04)

`executor_node` is gone; the compiled fan-out graph is registered directly as the
`executor` node with `checkpointer=None`, so the SH graph's existing SQLite
checkpointer owns its state. Chose subgraph-as-node over flattening after a probe
showed an interrupt inside a subgraph propagates to the parent's `__interrupt__`,
the parent's joiner is withheld, and `Command(resume=...)` on the parent finishes
the run with **no worker re-executed**.

Ported: dependency substitution, handoff injection and worker numbering into
`prepare_sends`; delegation records and timeline into `run_task`; the
once-per-task-per-round failure dedupe into `on_wave`; `majority_answer` as
`reduce_samples`.

Three defects caught while wiring, each of which would have shipped:

- **Lost concurrency bound.** Removing the ThreadPoolExecutor silently dropped
  `min(submissions, MAX_WORKERS)`. `SplunkConnectionPool` holds exactly 6
  connections, so an uncapped fan-out could starve it. Restored as
  `max_parallel=MAX_WORKERS`, which keeps a task's samples in one wave so the
  majority vote still reduces correctly.
- **`majority_answer` can return `None`** when there is no majority; the old code
  guarded it with `winner or res_list[0]` and the new `collect` did not. Caught by
  the type checker, not by a test.
- **Ignored interrupt.** The subgraph's hitl node interrupts rather than raising,
  so `invoke()` *returns* with `__interrupt__` set. `run_sh` ignored it and would
  have returned an empty answer, silently continuing past the failure a human was
  being asked about — a regression introduced by deleting `executor_node`'s own
  pause. `run_sh` now takes `run_dir` and loops on `__interrupt__` via
  `hitl.resolve_interrupt`, preserving the tty / non-tty front-ends.

Suite: **178 passed**. Not integration-tested — the Splunk licence is still
expired. LangSmith trace nesting across the new fan-out is also unverified; the
run tree is captured in `prepare_sends` and passed per payload, but only a live
run will confirm workers nest under the SH trace.

## Every SH LLM node reaches the graph interrupt (2026-09-06)

User-directed: put every LLM call site behind the same resumable interrupt, and
collapse the two coexisting pause mechanisms into one.

Clarification on the premise: `verifier` and `adjudicator` were *already* graph
nodes. The gap was that they still used `RunPaused` (a raised exception, a JSON
side-record, and a dead process) rather than the checkpointed interrupt, so a
provider outage there lost the question's work and was not resumable.

**Why they could not simply call `interrupt()` in place** — the same constraint
that shaped the executor: `interrupt()` restarts its own node from the top, and
both nodes call `_run_senior` *before* the failure is detectable. Interrupting
inline would re-issue that worker's LLM call on every resume. So each node now
**marks `api_error` into state and returns**, and a single side-effect-free
`sh_hitl` node does the interrupting. Resuming replays only `sh_hitl`.

The adjudicator returns its marker *alongside* the adjudication it already paid
for, so a pause never discards completed work.

Routing: `verifier` and `adjudicator` both gain a conditional edge to `sh_hitl`;
`sh_hitl` routes back by decision — `abort` to END, `retry` to the origin node
(re-running that worker is the point of retry, and only that node replays),
`skip` onward down the origin's normal path without re-entering it.

**Collapsed to one mechanism.** `hitl.request_decision` and
`hitl.pause_if_api_failed` had no production callers left and were removed with
their tests; `hitl.py` is now just `RunPaused` + `resolve_interrupt`, and
`orchestrator._pause_if_api_failed` is gone. The previously noted wart of "two
pause mechanisms coexisting" is closed.

New test `test_every_sh_llm_node_can_reach_the_graph_interrupt` asserts both that
`verifier`/`adjudicator` have edges *into* `sh_hitl` and that `sh_hitl` has edges
back *out* to them (without which `retry` would be unreachable). Suite:
**176 passed** (179 minus the 3 tests for the removed functions).

Still not integration-tested — the Splunk licence remains expired.
