# SIEM Agent v1.2 — Persistence + Extractor Simplification

> **Code**: `agent/v1/`
> **Predecessor**: [v1.1](v1.1.md) — LLMCompiler SH + parallel Senior workers + GLM-5.2 + token tracking.
> **Status**: In progress — no full `run_all_v1.py` run yet. This doc is a running changelog;
> every change lands here as it's made, and gets folded into a "What changed vs v1.1" summary
> once the version is closed out by its first full run.

## Changelog

- **Extractor outage resilience (run_1.2 crash fix)**. The first run_1.2 attempt died on Q200:
  Vultr's DeepSeek endpoint returned nginx `504 Gateway Time-out` for all 3 extractor retry
  attempts (2s/4s backoff too short for a real gateway outage) and the uncaught
  `InternalServerError` killed the whole run — with SH's correct answer in hand. Two changes:
  (1) `extractor.py` retry bumped to 5 attempts, 10s initial backoff doubling (rides out
  ~2.5 min outage); (2) `run_all_v1.py` wraps `extractor.extract` in try/except — on final
  failure it falls back to the last non-empty line of the SH answer, emits an
  `extract_failed` event, and continues the run instead of crashing.

- **Extractor model swap: DeepSeek-V4-Flash → Qwen3.6-27B (thinking disabled)**. DeepSeek's
  Vultr serving cluster went hard-down mid-run_1.2 (chat completions hang → 504; `/models` and
  GLM fine). User approved swap. Qwen3.6-27B is hybrid-reasoning — without
  `chat_template_kwargs.enable_thinking=false` it returns `content: null` with all budget in
  hidden CoT; verified live that disabling thinking yields clean bare answers ('Blue' probe).
  `EXTRACT_EXTRA_BODY` passed via `extra_body` only when the model is the Qwen default.

- **Verifier iteration cap + loud failure (user request)**. The verifier's Senior worker
  inherited the >=500pt 25-iteration budget despite its <=3-query mandate. Now capped at
  `VERIFIER_MAX_ITER = 8` (`run_senior`/`_run_senior` gained a `max_iter` override). A
  verifier worker that fails/caps/crashes can no longer influence the answer: original kept,
  `[SH VERIFIER] VERIFIER FAILED` printed, `verifier_failed` event emitted for post-run
  review. Takes effect on next process start (run in flight uses the loaded module).

- **Grounding guard rejected every comma-joined list answer (run_1.2 attempt-2 Q200)**.
  `is_grounded` required the WHOLE answer string as a verbatim substring of evidence, but
  scoreboard list answers are comma-joined while worker evidence lists values as
  prose/bullets — `bstoll,btun,splunk_access,web_admin` can never appear verbatim. Every
  correct list answer failed grounding → replan churn → rounds exhausted. Fix: for
  comma-joined answers, every component must appear somewhere in evidence (fabricated
  components still fail — anti-fabrication unchanged). Regression tests added to
  `tests/test_grounding.py`.

- **Joiner last-line fallback submitted a replan task description (run_1.2 attempt-2 Q200)**.
  When the joiner asks to REPLAN with rounds exhausted, the fallback branch took the last
  non-empty line of the joiner's replan text — a task description ("2. Run a focused
  exclusion check: ...") — as the final answer; the extractor dutifully distilled it to
  `frothly_admin,mkraeus` (0/100 with two solved workers holding the right answer). The
  fallback now prefers `best_candidate` over ALL of the question's delegations
  (`ctx.q_delegations`, every round) and only degrades to last-line extraction when no
  worker produced any answer.

- **CRITICAL: verifier/joiner judged answers against the wrong question (run_1.2 Q202)**.
  Both `verifier_node` and the joiner grounding check derived the question text via
  `next(m for m in state["messages"] if isinstance(m, HumanMessage))` — the FIRST
  HumanMessage in the persistent cross-question thread, i.e. always the run's first question
  (Q200). On Q202 the verifier received SH's correct answer (`Intel ... E5-2676 v3`), checked
  it against Q200's IAM-users question, "refuted" it, re-ran Q200's investigation, and
  substituted Q200's answer — a 500-pt question lost with the right answer in hand. Hidden in
  v1.1 because MemorySaver + repeated crashes kept the thread fresh; SqliteSaver persistence
  exposed it. Fix: `DelegationContext` now carries `current_question` (set by
  `reset_question(qid, points, question)` from the runner); verifier and joiner grounding read
  `ctx.current_question` instead of scanning the thread. Regression tests in
  `tests/test_current_question.py`.

- **Bounded SH history window (`MAX_HISTORY_MSGS = 24`)**. With persistence actually working,
  every SH planner/joiner call replayed the entire cross-question transcript: Q202 (third
  question of the run) burned 1,034,129 SH input tokens — $0.95 on one question, worse every
  subsequent question (quadratic over the run). `_window()` now feeds only the last 24
  messages (~3-5 prior questions of context) to the planner/joiner LLM calls; the checkpoint
  itself still stores full history.

- **SQLite-backed cross-question memory (`SqliteSaver`)**. v1.1's SH used LangGraph's
  `MemorySaver`, which lives only in process RAM — every time the runner process was killed and
  resumed (external kills happened repeatedly during the v1.1 full run), the SH's entire
  cross-question memory thread was silently wiped, and the next question's planner started from
  a blank slate instead of seeing prior questions' plans/findings/answers. Fixed by swapping to
  `langgraph_checkpoint_sqlite.SqliteSaver`, writing checkpoints to
  `<run_dir>/sh_checkpoints.sqlite`. `build_sh_agent_compiler()` now takes an optional
  `checkpoint_db_path`; when set, checkpoints persist to disk and survive process restarts.
  Verified with a real two-process test: process 2's SH plan explicitly referenced process 1's
  prior answer after a full process restart.

- **`run_summary.json` resume-merge**. Previously a resumed run (`--start Qxxx --run-name
  <name>`) overwrote `run_summary.json` with only the new segment's data, losing the prior
  segment's results, score, and token/cost totals from view (the scoreboard's own
  `scoreboard_submissions.json` was still cumulative and remained the source of truth, but the
  summary file misrepresented the run). `run_all_v1.py` now loads the existing
  `run_summary.json` at startup if present and seeds `results`, `score`, `total`,
  `failed_delegations`, and token/cost counters from it; new questions append instead of
  replacing. Added `UsageTracker.seed()` to pre-load token/cost counters from a prior segment's
  saved totals (recomputing cost from raw token counts rather than trusting the old dollar
  figure, so a stale price table at seed time doesn't propagate forward). Also fixed a latent
  bug in `UsageTracker.totals()` where the `combined` per-model dict was built via a naive
  `{**self._models, **self._nim}` spread that silently clobbered overlapping model keys instead
  of summing them — not reachable until seeding made overlaps possible. Verified end-to-end with
  two separate process launches sharing one `--run-name`: final `run_summary.json` showed both
  questions merged, additive score, and additive token/cost totals.

- **Remove extractor validation node.** The Extractor no longer validates the SH's answer
  against the question's format guidance or asks the SH to retry on rejection — it only strips
  prose down to the bare answer now (`Extractor.extract()`; `validate()` and `process()` are
  gone). `run_all_v1.py`'s per-question loop calls `extractor.extract()` once and submits
  directly; the `EXTRACTOR_MAX_RETRIES` retry loop, `extractor_rejections` counter (console
  output, timeline, `run_summary.json`), and the `_NON_ANSWER` regex are all removed.

- **Per-(qid, role, model) usage attribution (`UsageTracker`).** Previously only SH tokens were
  broken out per question (`_sh_cum`/`_sh_snap`); Senior worker and Extractor cost had no way to
  be attributed back to a question. Added `UsageTracker._by_q: dict[(qid, role), bucket]` plus a
  `_add_by_q()` helper; `on_llm_end()` now derives `role` ("sh"/"senior"/"other") and `qid` (the
  tag starting with `"Q"`) from the LangChain callback's `tags` kwarg and records into `_by_q`
  alongside the existing `_models`/`_sh_cum` bookkeeping (unchanged). `add_nim_usage()` gained
  `qid`/`role` kwargs (default `role="extractor"`) so the Extractor's raw-SDK calls also land in
  `_by_q`. New `by_question()` method returns `{qid: {role: bucket}}`. `Extractor.extract()`
  gained an optional `qid` param forwarded to `add_nim_usage()`; `run_all_v1.py`'s call site
  updated to pass `qid=qid`. Verified with `agent/v1/tests/test_usage_attribution.py` (3 new
  tests) plus the full `agent/v1/tests/` suite (15 passed) to confirm `totals()`, `_sh_cum`, and
  `seed()` are unaffected.

- **Wire the canonical event stream into `run_all_v1.py`; add `metrics.json`; split
  `run_summary.json`.** `main()` now emits `run_start` (git sha, models, `resumed` flag) after
  `extractor`/`ls_project` are defined, then `question_start`/`submit`/`question_end` per
  question, and `run_end` after the loop — all via `logger.events` (the `EventLog` from Task 2/3).
  Added module-level pure `build_metrics_row()` (unit-tested in
  `agent/v1/tests/test_metrics_row.py`) that assembles a per-question row — `grounded` (does the
  submitted answer appear verbatim in any worker's answer text — the fabrication signal),
  `statuses`, `cap_hits`, `latency_s` (per-stage + total, from `logger.events.timer()` wrapping
  the SH and Extractor calls), and `cost_by_role` (from `tracker.by_question()`). Rows accumulate
  in `metrics_rows` and are rewritten to `<run_dir>/metrics.json` every question. The heavy
  per-question record (question text, full SH answer, delegations) now writes to
  `<run_dir>/questions/<qid>.json` instead of living in `run_summary.json`'s `results` array;
  `run_summary.json` is now a light rollup (`schema_version`, score/total/correct/attempted/
  failed_delegations/token_usage/models, `questions_dir`, and a compact `index` list of
  `{id, verdict, earned, grounded}`). Resume logic preserved: in addition to seeding
  `total`/`score`/`failed_delegations`/token usage from the prior `run_summary.json`, `results`
  is now reconstructed by reloading each prior question's `questions/<qid>.json` via the resumed
  summary's `index`, and `metrics_rows` is seeded from an existing `metrics.json` if present. No
  scoring logic changed — scoreboard submit, `earned_pts`/`total_points` accounting, and the
  correct/wrong verdict are untouched; only instrumentation was added around them. Verified with
  `agent/v1/tests/test_metrics_row.py` (2 new tests) plus the full suite (17 passed), and a live
  smoke run (`python agent/v1/run_all_v1.py --ids Q200,Q301`, `SIEM_LOG_ROOT` pointed outside
  OneDrive) that produced `events.jsonl` with the full run_start→question_start→submit→
  question_end→run_end lifecycle, `metrics.json` with `grounded`+`latency_s` for both questions,
  `questions/Q200.json` and `questions/Q301.json`, and a light `run_summary.json` — score matched
  expectations (Q200 correct/100pts, Q301 wrong/0pts).

- **Resume-path hardening (review fixes for the above).** (1) Per-question metrics writes are
  now idempotent by qid: extracted pure `upsert_metrics_row(rows, row)` which replaces any
  stale row for the same qid instead of blindly appending — prevents duplicate rows in
  `metrics.json` (and a stale-first-match `grounded` in the summary index) when a question is
  reprocessed after a crash-then-resume. (2) Old-schema resume compatibility: extracted pure
  `seed_resume_results(prior, questions_dir)` — new-schema summaries (with `index`) reload
  heavy records from `questions/<qid>.json`, while old-schema summaries (run_1.0/run_1.1,
  inline `results`, no `index`) fall back to the embedded `results` array directly instead of
  silently seeding an empty list. Both helpers unit-tested (5 new tests in
  `test_metrics_row.py`; full suite 22 passed). No scoring changes.

- **LangSmith hygiene: traceable Extractor + per-run project naming.** The Extractor previously
  called the raw OpenAI SDK directly, so its completion never appeared as a span in LangSmith.
  Extracted the network call into `Extractor._complete()` and wrapped it with
  `@traceable(run_type="llm", name="Extractor")` (with a no-op fallback decorator if `langsmith`
  fails to import, so the module still runs offline); retry logic and token tracking in
  `extract()` are unchanged — the decorator only adds a span. Also fixed `run_all_v1.py`, which
  hardcoded `LANGSMITH_PROJECT = "V1.1"` so every run's traces piled into one shared project —
  now set to `f"botsv3-{logger.run_name}"` (matches the per-run naming already documented and
  already used for `metrics.json`/event-stream data), set after `logger` exists and before the
  first `run_sh`/extractor call. The `resumed` flag on the `run_start` event (added in the task
  above) already covers tagging resumed attempts — no additional LangSmith-side metadata added,
  per plan. Verified: full suite still 22 passed; live smoke run
  (`python agent/v1/run_all_v1.py --ids Q200`, `SIEM_LOG_ROOT` outside OneDrive) completed
  correctly (Q200 scored 100/100), console and `run_summary.json` both show
  `LangSmith project: botsv3-test_<ts>` instead of `V1.1`, and `events.jsonl`'s `run_start` row
  carries the same `langsmith_project` value with `resumed: false`.

- **`make_report.py` — render `report.md` from the event stream.** New pure-rendering module:
  `load_events()`/`load_metrics()` read `events.jsonl`/`metrics.json`; `render_report()` builds a
  markdown doc with score (`correct/attempted` + pts), p50/p95/max latency, slowest and
  most-expensive question tables, the ungrounded-wrong-answer list (fabrication signal — a
  submitted value no worker ever produced), the iteration-cap-hit list, and a wrong/not-answered
  table; `main()` writes it to `<run_dir>/report.md`. No scoring or instrumentation logic
  changed — purely a downstream view. Verified with 2 new tests
  (`agent/v1/tests/test_make_report.py`: score/ungrounded-section assertions and
  slowest-questions ranking) plus the full suite (24 passed), and rendered a real report from a
  smoke-run dir (`test_20260707_024219`, Q200 correct/100pts) confirming all sections populate.

- **Fix dropped `iterations`/`cap_hit` seam between worker and delegation record.**
  `splunk_subagent.py`'s worker result dict already carried `iterations`/`cap_hit` (added in an
  earlier task), but `orchestrator.py`'s `executor_node` hand-built the `record` dict appended to
  `ctx.q_delegations` and only copied `status`/`answer`/`spl_used`/`sourcetypes`/`full_state`,
  silently dropping both fields — so `build_metrics_row`'s `cap_hits` count was always 0 in real
  runs and `make_report.py`'s iteration-cap section never populated, even though the
  hand-built-dict unit tests in `test_metrics_row.py` passed (they never exercised the real
  record-building path). Fixed by adding `"iterations": result.get("iterations", 0)` and
  `"cap_hit": result.get("cap_hit", False)` to the `record` dict, and making the crash-fallback
  `result = {...}` in the `except Exception` branch explicit about the same two keys (defaulted
  to `0`/`False`) so the shape is consistent whether or not the worker crashed. Verified with a
  new `agent/v1/tests/test_delegation_record_contract.py` (3 tests) that drives the real
  `SplunkWorkerPool.run_senior` → `_run` path with a mocked `run_agent_traced`, proving the
  worker result dict itself carries correct `iterations`/`cap_hit` values (e.g. `step_count=20 >
  MAX_ITER=15` → `cap_hit=True`) — closing the seam that the hand-built-dict tests couldn't catch.
  Full suite now 27 passed. No scoring logic touched.

- **Grounding guard in the joiner (anti-fabrication).** Added `agent/v1/grounding.py`
  (`is_grounded`/`best_candidate`, pure) and a new module-level `decide_joiner_answer()` in
  `orchestrator.py`. `joiner_node`'s `FINAL ANSWER:` branch now runs the extracted answer through
  `decide_joiner_answer(answer, task_results, question_text, plan_round=, max_rounds=)` before
  returning `done=True`: if the answer is not a verbatim (case-insensitive) substring of any
  worker's result or the question text, and replan rounds remain, it forces a REPLAN (new
  `needs_replan: bool` state key routes the joiner back to `planner`, not `executor`, via a new
  `"planner"` edge in the joiner's conditional-edge map); if no rounds remain, it falls back to
  the highest-confidence worker's own answer (`best_candidate`) instead of submitting the SH's
  fabricated value — this directly targets the v1.1 fabrication failure mode (Q221 'glacier',
  Q303 'tomcat7:...', Q330 'james', Q333 'cve-2018-7600', 2,300 pts lost). `needs_replan` is
  cleared (`False`) in both of `planner_node`'s return branches so it never leaks across
  questions/rounds. `route_joiner` checks `needs_replan` first, before the existing done/rounds/
  tasks checks. `JOINER_SYSTEM_PROMPT` gained a "GROUNDING RULE" paragraph as a prompt-level
  helper (the Python guard remains the enforcement). Existing paths preserved unchanged: Option B
  REPLAN (LLM-initiated, still goes straight to `executor`) and the "no FINAL ANSWER / REPLAN tag"
  last-line fallback. Verified: `agent/v1/tests/test_joiner_guard.py` (4 new tests) plus full
  suite (38 passed) and the module import check. Live smoke run
  (`run_all_v1.py --ids Q225,Q301`, `SIEM_LOG_ROOT` outside OneDrive): Q225 no longer submitted
  the old fabrication `taedonggang.jpeg`; instead of a clean grounded win, the run surfaced two
  **pre-existing, unrelated** issues that blocked a clean grounded answer for this question — (a)
  two Senior workers crashed on a Windows `charmap`/`UnicodeEncodeError` while printing an arrow
  character, and (b) `parse_plan()`'s `^(\d+)\.` regex doesn't match the indented sub-bullets
  (`  1. ...`) the joiner's own REPLAN template tells it to use, so a legitimate LLM-initiated
  Option B REPLAN silently produced zero parsed tasks and fell through to the last-line fallback
  — neither is caused by this task's change (the new grounding branch requires a `FINAL ANSWER:`
  tag to fire, which this run's joiner never emitted). Recommend follow-up tasks: fix the Windows
  console encoding crash in the Senior worker's print/log path, and make `parse_plan` tolerant of
  leading whitespace before the task number.

- **Fixed both follow-ups above.** (1) Added `force_utf8_stdio()` in `run_all_v1.py`, called at
  the top of `main()` before any printing — reconfigures `sys.stdout`/`sys.stderr` to UTF-8 with
  `errors="replace"`, so the Windows cp1252 console no longer raises `UnicodeEncodeError` on the

  `agent/v1/tests/test_parse_plan.py` (column-0 regression + indented tasks + indented `$N` dep
  extraction).

- **Answer-shape contract (planner -> extractor).** Targets the Q202-style failure where the
  extractor submitted `E5-2676 v3` for an official answer of `E5-2676` (vendor/version suffix not
  stripped). Extracted the extractor's inline prompt string into a pure module-level
  `build_extract_prompt(question, guidance, verbose_answer, expected_shape="")` in
  `extractor.py`; `Extractor.extract()` now accepts an additional `expected_shape: str = ""`
  param and calls the new function instead of building the string inline — the retry loop,
  `_complete`/`@traceable` span, and `add_nim_usage(qid=, role="extractor")` token tracking are
  all unchanged. `PLANNER_SYSTEM_PROMPT` in `orchestrator.py` gained an `EXPECTED SHAPE: <...>`
  output-line instruction (prompt-level helper only, not yet parsed out of SH state — deferred
  per plan). `run_all_v1.py`'s extractor call site now passes `expected_shape=guidance` (the
  existing `answer_guidance` field already carries format hints, so this is a zero-new-plumbing
  first pass; a later iteration can parse the planner's own `EXPECTED SHAPE:` line instead).
  Verified with 2 new tests in `agent/v1/tests/test_extractor_shape.py` plus the full suite (45
  passed). No scoring logic touched.

- **Raw-content tool + noise-filter prompt patch (`get_raw_events`).** Targets the content-read
  class (Q306/Q310/Q315/Q321/Q322 need to read email bodies, bash history, HTTP payloads) that
  the aggregation-only verify gate blocks today, plus the Q317 case where a `NOT match(...)`
  name-blocklist regex excluded the correct answer `HxTsr.exe`. Added a new `get_raw_events`
  `@tool` to `make_tools` in `agent/splunk_agent.py`: it clamps `limit` to
  `max(1, min(int(limit), 20))` before calling `splunk.sample_events(sourcetype=, index=,
  keyword=, count=n)` and returns `_format_result(result, keep_raw=True)`, and it is registered
  in `make_tools`'s returned tool list. Because `_verify_call`'s aggregation rule only applies to
  tool name `run_splunk_search`, the new tool is automatically exempt — the verify gate was NOT
  modified. `SYSTEM_PROMPT` gained two paragraphs before the example flow: content-reading
  guidance (use `get_raw_events` when the answer is text inside an event) and a noise-filter
  discipline paragraph (never exclude a process/file/host by benign-name blocklist; suspicion
  comes from behavior, not a name; do not add `NOT match(...)` filters that drop candidate
  answers). Verified with 2 new tests in `agent/v1/tests/test_raw_events_tool.py` (tool
  registered + `count` clamped to <=20) plus the full suite (47 passed). No scoring or
  verify-gate logic touched.

- **Keyless `web_lookup` tool for external-knowledge questions.** Targets Q213/Q302
  (Symantec vendor severity/date) and Q332/Q333 (CVE mapping), which need facts outside the
  BOTSv3 dataset. Added `agent/v1/web_tool.py`: `_fetch(query)` POSTs to DuckDuckGo's HTML
  endpoint (`https://html.duckduckgo.com/html/`), `_clean()` strips tags/unescapes entities, and
  the `@tool web_lookup(query)` function returns the top-5 cleaned `result__snippet` matches
  joined by `" | "`, or a graceful `"web_lookup unavailable (...)"` / `"web_lookup: no result
  snippets found."` string on any fetch/parse failure — never raises, so offline runs and unit
  tests can't be broken by network flakiness. Wired the tool to workers without touching v0's
  global tool list: `create_agent()` in `agent/splunk_agent.py` gained an `extra_tools: list |
  None = None` param, appended to `tools` (before `tool_map` is built and before
  `llm.bind_tools`) only when passed; `SplunkWorkerPool.__init__` in `agent/v1/splunk_subagent.py`
  now imports `web_lookup` and passes `extra_tools=[web_lookup]` into its `create_agent(...)`
  call, and `ESCALATE_INSTRUCTIONS` gained a one-line mention that `web_lookup` exists for
  external facts only. No verify-gate change needed — `_verify_call`'s aggregation rule only
  inspects `run_splunk_search` calls, so a plain function tool like `web_lookup` is automatically
  exempt, and the Intention protocol is checked on the message, not the tool name. Verified with 2
  new tests in `agent/v1/tests/test_web_tool.py` (snippet extraction via a mocked `_fetch`;
  graceful degradation on a mocked exception) plus the full suite (49 passed) and an import check
  of `splunk_subagent`. No scoring logic touched.

- **Points-aware iteration budget + cap-to-PARTIAL discipline.** Targets the v1.1 finding that
  46/56 questions got identical effort and five of eight 1000-pt questions were wrong, and that
  Q328/Q332/Q333 guessed a bare (fabricated) `FINAL ANSWER` the moment the iteration cap hit
  instead of admitting uncertainty. Added module-level `iter_budget(points) -> int` in
  `agent/splunk_agent.py` (`25` if `points >= 500` else module `MAX_ITER` (15)). `create_agent()`
  gained a `max_iter: int = MAX_ITER` param; the two closure-scoped iteration-cap checks that
  previously read the module constant — `agent_node`'s `if step > MAX_ITER` and
  `should_continue`'s `if state.get("step_count", 0) > max_iter` — now read the local `max_iter`
  instead, so each compiled graph instance can carry its own budget. The forced-final message
  fired when the cap is hit no longer says "give your best final answer" (the v1.1 guess-at-cap
  bug); it now demands `PARTIAL ANSWER: <candidate>, UNCERTAINTY: <...>, SPL: <...>` or `ESCALATE`,
  matching the existing ESCALATE protocol's vocabulary so `_classify()` still parses the result as
  `partial`/`too_big` rather than a false `solved`. `run_agent_traced()` also gained a
  `max_iter: int = MAX_ITER` param used to scale `recursion_limit = max_iter * 4` — a >=500pt
  worker graph running to 25 iterations needs a higher LangGraph recursion ceiling than the
  default 60, otherwise it would hit LangGraph's own limit before its iteration cap fired.
  Points are threaded end-to-end with a minimal-diff path: `run_all_v1.py`'s existing
  `ctx.reset_question(qid)` call site now passes `points=points`; `DelegationContext.reset_question`
  gained a `points: int = 0` param and stores `self.current_points` (no change to `run_sh`'s
  signature — `ctx` is already shared/captured by the SH graph closure, so `run_sh` never needed
  points itself); `_run_senior()` now calls `ctx.pool.run_senior(subquestion, ctx.current_qid,
  idx, points=ctx.current_points)`. `SplunkWorkerPool.__init__` builds **two** Senior graphs once
  (`self.senior_graph` at `max_iter=MAX_ITER`, `self.senior_graph_hi` at
  `max_iter=iter_budget(HIGH_VALUE_THRESHOLD)` where `HIGH_VALUE_THRESHOLD = 500`) — both share the
  identical `extra_instructions=ESCALATE_INSTRUCTIONS` and `extra_tools=[web_lookup]`, only
  `max_iter` differs; `run_senior(subquestion, parent_qid, idx, points=0)` picks
  `senior_graph_hi` when `points >= HIGH_VALUE_THRESHOLD` else `senior_graph`, and forwards the
  matching `max_iter` into `_run()`/`run_agent_traced()` so the recursion limit and the iteration
  cap agree. Verified with 2 new tests in `agent/v1/tests/test_budget.py`
