# SIEM Agent v1.2 — Persistence + Extractor Simplification

> **Code**: `agent/v1/`
> **Predecessor**: [v1.1](v1.1.md) — LLMCompiler SH + parallel Senior workers + GLM-5.2 + token tracking.
> **Status**: In progress — no full `run_all_v1.py` run yet. This doc is a running changelog;
> every change lands here as it's made, and gets folded into a "What changed vs v1.1" summary
> once the version is closed out by its first full run.

## Changelog

- **SQLite-backed cross-question memory (`SqliteSaver`)**. v1.1's SH used LangGraph's
  `MemorySaver`, which lives only in process RAM — every time the runner process was killed and
  resumed (external kills happened repeatedly during the v1.1 full run), the SH's entire
  cross-question memory thread was silently wiped, and the next question's planner started from
  a blank slate instead of seeing prior questions' plans/findings/answers. Fixed by swapping to
  `langgraph_checkpoint_sqlite.SqliteSaver`, writing checkpoints to
  `<run_dir>/sh_checkpoints.sqlite`. `build_sh_agent_compiler()` now takes an optional
  `checkpoint_db_path`; when set, checkpoints persist to disk and survive process restarts.
  Verified with a real two-process test: process 2's SH plan explicitly referenced process 1's
  prior answer after a full process restart.

- **`run_summary.json` resume-merge**. Previously a resumed run (`--start Qxxx --run-name
  <name>`) overwrote `run_summary.json` with only the new segment's data, losing the prior
  segment's results, score, and token/cost totals from view (the scoreboard's own
  `scoreboard_submissions.json` was still cumulative and remained the source of truth, but the
  summary file misrepresented the run). `run_all_v1.py` now loads the existing
  `run_summary.json` at startup if present and seeds `results`, `score`, `total`,
  `failed_delegations`, and token/cost counters from it; new questions append instead of
  replacing. Added `UsageTracker.seed()` to pre-load token/cost counters from a prior segment's
  saved totals (recomputing cost from raw token counts rather than trusting the old dollar
  figure, so a stale price table at seed time doesn't propagate forward). Also fixed a latent
  bug in `UsageTracker.totals()` where the `combined` per-model dict was built via a naive
  `{**self._models, **self._nim}` spread that silently clobbered overlapping model keys instead
  of summing them — not reachable until seeding made overlaps possible. Verified end-to-end with
  two separate process launches sharing one `--run-name`: final `run_summary.json` showed both
  questions merged, additive score, and additive token/cost totals.

- **Remove extractor validation node.** The Extractor no longer validates the SH's answer
  against the question's format guidance or asks the SH to retry on rejection — it only strips
  prose down to the bare answer now (`Extractor.extract()`; `validate()` and `process()` are
  gone). `run_all_v1.py`'s per-question loop calls `extractor.extract()` once and submits
  directly; the `EXTRACTOR_MAX_RETRIES` retry loop, `extractor_rejections` counter (console
  output, timeline, `run_summary.json`), and the `_NON_ANSWER` regex are all removed.

- **Per-(qid, role, model) usage attribution (`UsageTracker`).** Previously only SH tokens were
  broken out per question (`_sh_cum`/`_sh_snap`); Senior worker and Extractor cost had no way to
  be attributed back to a question. Added `UsageTracker._by_q: dict[(qid, role), bucket]` plus a
  `_add_by_q()` helper; `on_llm_end()` now derives `role` ("sh"/"senior"/"other") and `qid` (the
  tag starting with `"Q"`) from the LangChain callback's `tags` kwarg and records into `_by_q`
  alongside the existing `_models`/`_sh_cum` bookkeeping (unchanged). `add_nim_usage()` gained
  `qid`/`role` kwargs (default `role="extractor"`) so the Extractor's raw-SDK calls also land in
  `_by_q`. New `by_question()` method returns `{qid: {role: bucket}}`. `Extractor.extract()`
  gained an optional `qid` param forwarded to `add_nim_usage()`; `run_all_v1.py`'s call site
  updated to pass `qid=qid`. Verified with `agent/v1/tests/test_usage_attribution.py` (3 new
  tests) plus the full `agent/v1/tests/` suite (15 passed) to confirm `totals()`, `_sh_cum`, and
  `seed()` are unaffected.

- **Wire the canonical event stream into `run_all_v1.py`; add `metrics.json`; split
  `run_summary.json`.** `main()` now emits `run_start` (git sha, models, `resumed` flag) after
  `extractor`/`ls_project` are defined, then `question_start`/`submit`/`question_end` per
  question, and `run_end` after the loop — all via `logger.events` (the `EventLog` from Task 2/3).
  Added module-level pure `build_metrics_row()` (unit-tested in
  `agent/v1/tests/test_metrics_row.py`) that assembles a per-question row — `grounded` (does the
  submitted answer appear verbatim in any worker's answer text — the fabrication signal),
  `statuses`, `cap_hits`, `latency_s` (per-stage + total, from `logger.events.timer()` wrapping
  the SH and Extractor calls), and `cost_by_role` (from `tracker.by_question()`). Rows accumulate
  in `metrics_rows` and are rewritten to `<run_dir>/metrics.json` every question. The heavy
  per-question record (question text, full SH answer, delegations) now writes to
  `<run_dir>/questions/<qid>.json` instead of living in `run_summary.json`'s `results` array;
  `run_summary.json` is now a light rollup (`schema_version`, score/total/correct/attempted/
  failed_delegations/token_usage/models, `questions_dir`, and a compact `index` list of
  `{id, verdict, earned, grounded}`). Resume logic preserved: in addition to seeding
  `total`/`score`/`failed_delegations`/token usage from the prior `run_summary.json`, `results`
  is now reconstructed by reloading each prior question's `questions/<qid>.json` via the resumed
  summary's `index`, and `metrics_rows` is seeded from an existing `metrics.json` if present. No
  scoring logic changed — scoreboard submit, `earned_pts`/`total_points` accounting, and the
  correct/wrong verdict are untouched; only instrumentation was added around them. Verified with
  `agent/v1/tests/test_metrics_row.py` (2 new tests) plus the full suite (17 passed), and a live
  smoke run (`python agent/v1/run_all_v1.py --ids Q200,Q301`, `SIEM_LOG_ROOT` pointed outside
  OneDrive) that produced `events.jsonl` with the full run_start→question_start→submit→
  question_end→run_end lifecycle, `metrics.json` with `grounded`+`latency_s` for both questions,
  `questions/Q200.json` and `questions/Q301.json`, and a light `run_summary.json` — score matched
  expectations (Q200 correct/100pts, Q301 wrong/0pts).
