# v1.5 — the premise ledger

**In progress.** Spec: `docs/superpowers/specs/2026-09-20-premise-ledger-design.md`.
Plan: `docs/superpowers/plans/2026-09-20-premise-ledger.md`.

v1.5 replaces the senior's prose `## Assumptions` section, and the five regexes that
read it, with one runner-owned structured premise ledger. The root cause it targets is
v1.4.2's Q216 loss: a premise cannot be laundered out of existence by writing a
cleaner report next round, because the senior never re-emits the list.

## Changelog

- **Probed GLM-5.3 on AI& for nested tool arguments (2026-09-20).** `submit_finding`
  took only flat primitives, and the whole ledger design depends on the senior being
  able to emit a list of objects. A one-off probe bound a tool with
  `new_premises: list[dict]` and `open_questions: list[str]` to `zai-org/glm-5.3` at
  `https://api.aiand.com/v1` and asked for two premises and one question.

  Result: **nested objects work.** The model returned
  `[{'kind': 'other', 'load_bearing': True, 'text': 'The flow is inbound-heavy.'},
  {'kind': 'definition', 'load_bearing': False, 'text': 'Port 3333 alone does not
  prove the activity.'}]` — every field present, both kinds correct, both booleans
  correct — and `open_questions` as a plain list of strings.

  So `submit_finding` types `new_premises` and `premise_updates` as `list`, and the
  JSON-string fallback in spec §5 is not needed. `finding._coerce_objects` still
  accepts a JSON string as cheap insurance against a provider changing its mind.

  (The probe first failed with `model_not_found` against `glm-5.3`: the id on AI& is
  `zai-org/glm-5.3`, as `run_all_v1.SENIOR_MODEL` already had it.)
